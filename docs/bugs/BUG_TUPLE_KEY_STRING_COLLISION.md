# BUG: Tuple-Key String Collisions in NOT/OR Dedup Paths

**Date**: 2026-04-16
**Severity**: Correctness (High)
**Status**: Resolved 2026-04-16
**Affected**: NOT/NOT-JOIN filtering, OR union dedup, helper paths that key tuples via string concatenation

## Summary

Several executor paths build tuple identity keys using `fmt.Sprintf("%v", value)` joined by `"|"`.
This keying scheme is not injective: different tuples can map to the same key string.
When collisions happen, the engine can silently deduplicate distinct tuples or incorrectly treat
rows as matched in anti-join filtering.

## Root Cause

Tuple keys are generated by string concatenation without escaping or structural encoding:

```go
func notOrTupleKey(tuple Tuple) string {
    if len(tuple) == 0 {
        return ""
    }
    key := fmt.Sprintf("%v", tuple[0])
    for i := 1; i < len(tuple); i++ {
        key += fmt.Sprintf("|%v", tuple[i])
    }
    return key
}
```

This appears in dedup and anti-join style operations:

- `unionRelations(...)` (`helpers.go`) dedups OR branch results
- `getUniqueCombinations(...)` (`helpers.go`) dedups combo tuples
- `filterWithNotClause(...)` and `filterWithNotJoinClause(...)` (`query_executor.go`) track matched keys

## Collision Example

Two distinct tuples can produce identical keys:

- Tuple A: `["a|b", "c"]` → key `"a|b|c"`
- Tuple B: `["a", "b|c"]` → key `"a|b|c"`

These are different tuples, but the key function treats them as the same row.

## Expected Behavior

Tuple identity used for dedup/filter logic should be collision-safe for all supported
value types and values.

## Actual Behavior

When a collision occurs:

- OR union dedup can drop valid distinct tuples
- NOT/NOT-JOIN matched-key sets can incorrectly filter non-matching rows
- Unique combination extraction can undercount distinct input combinations

No error is emitted; behavior is silently wrong.

## Why This Is Subtle

- Most values do not contain delimiter-like strings, so failures are data-dependent.
- Bugs only manifest when key collisions align with query shape (OR/NOT paths).
- Test suites that focus on numeric/simple literals can miss this entirely.

## Reproduction Sketch

Minimal unit-level reproduction (dedup collision):

1. Build two relations whose projected tuples are `["a|b", "c"]` and `["a", "b|c"]`
2. Call `unionRelations(...)`
3. Observe output has length `1` instead of `2`

Minimal semantic reproduction (NOT collision):

1. Construct inner match key from `["a|b", "c"]`
2. Construct outer tuple key from `["a", "b|c"]`
3. `filterWithNotClause` treats outer row as matched and incorrectly filters it

## Fix Direction

Replace string-concatenated keys with a collision-safe tuple encoding:

- Length-delimited binary encoding per element (type + length + bytes), or
- Stable structured hashing over typed values, or
- Reuse existing tuple key/map primitives if already canonicalized elsewhere

The fix must preserve type distinctions and element boundaries.

## Verification Plan

Add regression tests that currently fail:

- `TestUnionRelations_NoKeyCollisionWithDelimiterValues`
- `TestNotClause_KeyCollisionDoesNotFilterDistinctTuple`
- `TestGetUniqueCombinations_NoCollisionAcrossTupleBoundaries`

Also include cross-type cases (`string`, `[]byte`, keywords, refs) to ensure
keying remains unambiguous across value domains.

## Resolution

**Resolved**: 2026-04-16

### Root cause confirmed

`notOrTupleKey` was a parallel implementation of an abstraction that already
existed in the same package. `TupleKey` and `TupleKeyMap`
(`datalog/executor/tuple_key.go`) — used by hash joins, symmetric hash
joins, and relation deduplication — provide an FNV-1a hash over typed
values with collision resolution through `datalog.ValuesEqual`. The
existing primitive is collision-safe by construction and independent of
any value-to-string encoding.

### Fix

Migrated all six call sites of `notOrTupleKey` to `TupleKey` /
`TupleKeyMap`:

- `datalog/executor/helpers.go`
  - `getUniqueCombinations` (1 site)
  - `unionRelations` (1 site)
- `datalog/executor/query_executor.go`
  - `filterWithNotClause` (2 sites: `matchedKeys` build + filter pass)
  - `filterWithNotJoinClause` (2 sites: same)

`notOrTupleKey` was deleted. The `fmt` import in `helpers.go` was removed
(only consumer was the deleted function).

### Test coverage added

`datalog/executor/tuple_key_collision_test.go` exercises four adversarial
value categories that all collide under the legacy stringification scheme:

| Category | Example pair |
|---|---|
| Delimiter shifts inside content | `["a\|b", "c"]` vs `["a", "b\|c"]` |
| Cross-type numeric (int vs string) | `[int64(5), "x"]` vs `["5", "x"]` |
| Cross-type bool vs string | `[true, "x"]` vs `["true", "x"]` |
| Cross-type float vs string | `[3.14, "x"]` vs `["3.14", "x"]` |

Tests cover three levels:

1. **Direct unit tests** — `getUniqueCombinations` and `unionRelations` with
   each adversarial pair
2. **Baseline tests** — `TupleKeyMap` correctly distinguishes the same
   adversarial pairs (proves the migration target works); `[]byte` values
   are distinguished by content via the `ValuesEqual` fallback even though
   `hashValue`'s default case puts each `[]byte` in a different bucket
   (correctness-safe; perf cliff is documented but not fixed here)
3. **End-to-end** — NOT-JOIN with pipe-bearing string values; verifies
   user-visible behavior does not silently filter the wrong tuples

All 14 assertions in the new file fail against the pre-fix code and pass
against the post-fix code. Full test suite (`./...`) is green.

### Why this took ~4 months to surface

The pattern was identical to the **Cache Path CardinalityOne Tombstone Gap**
already documented in `CLAUDE.md` (Bug Fixes and Learnings):

> When multiple code paths resolve the same semantic operation, tests must
> cover ALL paths. Test quantity and scenario variety mean nothing if they
> all exercise the same code path.

Two parallel implementations of "tuple set membership" both existed:
`TupleKey`/`TupleKeyMap` (production hot paths, well-tested) and
`notOrTupleKey` + `map[string]bool` (NOT/OR/union paths, no direct tests).
Test data across all NOT/OR/union tests used "happy values" (short English
names, integers, booleans, L85-encoded entity IDs, keywords) — none could
populate the bytes that the `|` delimiter occupied. The bug class was
structurally unreachable from the existing test corpus.

### Affected versions

The bug existed from commit `3e68dbc` (2025-12-18, "Implement NOT/OR
clauses for Datomic-compatible logical operations") through this fix.
