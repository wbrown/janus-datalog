# Scope Execution and the Engine's Contracts

This document states how the executor runs a nested scope, and the contracts the engine keeps while it does. A nested scope is a branch of an `or-join` or an `or-default-join`, a `not-join` body, or a subquery's inner query. `NESTED_SCOPES_AS_QUERIES.md` states the language and the inference that writes every form's header, and its §5.4 points here for the evaluation. `RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §1 states the rules and recursion the scopes evaluate.

## 1. Goals

The goals of `NESTED_SCOPES_AS_QUERIES.md` §1 stand. This design adds these.

1. Rules serve a caller at per-call cost. A query invoking a rule set runs on every call, at a cost the caller measures as its gate. The shapes are three. Reachability is a recursive rule bound by every member of a collection input. Readiness is derived with stratified negation and a recursive propagation rule. A loop in the caller's language is replaced by one query over a rule set whose body holds an `or-join`, seeded by a collection input. §7 states the acceptance tests.
2. A bound invocation costs one rewrite and one evaluation, and that evaluation derives each tuple once, wherever the invocation stands. Its seeds arrive as one relation or as the windows of §4.2 (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §1.3). The failure this removes: an invocation under `not`, `not-join`, `or`, `or-join` or `or-default` reran the fixpoint once per outer combination, where one rewrite seeded by every bound value derives the same tuples once. A fixpoint per subject tuple is that shape again.
3. The overlay matcher of `RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §3.1 composes with `SourceRouter`, predicate pushdown and the EA cache unchanged. Every read path the executor takes is one the overlay covers. So a cache lookup may stand in for a scan only under the conditions the matcher states for it.
4. The witnesses of `RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §2 record, per derived tuple, the rule and the body tuples of one derivation, the least of minimum depth. `WhyNot` descends a rule's alternatives one at a time to the clause that produced no match. Their substrate is two things. One is the scans of a planned query, which the witness rewrite extends with a fourth position bound to the matched datom's ElementID (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §2.1). The other is the fixpoint's record of each derived tuple's derivation (the same section, under Rules). Every scope in this design is planned through `QueryPlanner.PlanQuery` (§4.1).
5. One grammar (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §6). Every form the inference writes is a form an author may write. The parser, the builder, `Prepare` and the executor accept and refuse the same text.
6. Every error names the author's repair (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §5). A refusal that records a mechanism's limitation is not an error about the query.
7. Cost is measured, never claimed (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §7). An option that is off costs nothing.
8. The optimizer never changes results. Every test of this design runs under the optimizer-mode matrix of `RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §0.
9. The engine's contracts are the tests §7 names. A change that drops a contract names the failure it removes. A mechanism is not a contract. Three mechanisms are excluded: computing a form's interface from what a reader holds (`NESTED_SCOPES_AS_QUERIES.md` §4), choosing how a branch runs from the shape of its clauses, and binding into a branch what the form's header does not name (§4.2, §4.3).
10. A query is planned once per database per distinct prepared query, rule set and the symbols bound when the plan is made, whatever its inputs bind. The alternative is a plan made under a bound symbol kept out of the cache. Under it a query with a non-empty input is planned again on every execution.

## 2. The language

§2.1 to §2.5 of `NESTED_SCOPES_AS_QUERIES.md` stand. Two amendments state what the inference already writes.

### 2.1 A header of required variables alone

`(or-join [[?e ?f]] b1 b2)` and `(or-default-join [[?e ?f]] b1 b2)` are legal. The form keeps a tuple of the required run when a branch answers for it, and binds nothing. The `or-join` takes every branch's answer for every tuple. The `or-default-join` answers a tuple from the first branch with a result for it. Which branches are evaluated for a tuple is §4.2's. A `not-join` header is all required by definition.

The inference writes this header, by the rule of `NESTED_SCOPES_AS_QUERIES.md` §2.3, for a headerless form none of whose shared variables every branch binds. `[?e :a _] [?f :b _] (or-default [?e :x _] [?f :y _])` infers `(or-default-join [[?e ?f]] [?e :x _] [?f :y _])`. An `or` of predicates over a variable a pattern binds, `[?e :n ?n] (or [(> ?n 3)] [(< ?n 2)])`, infers `(or-join [[?n]] [(> ?n 3)] [(< ?n 2)])`. That is the shape `TestOrJoinWithARequiredOnlyHeaderFiltersTheOuter` tests. A refusal of the header would reject a query the language answers. The query `TestOrBranchExpressionIsOrderedAfterItsBinder` runs infers to `(or-default-join [[?a]] (and [(identity ?l) ?x] [?l :k :q]) (and [?m ?a _] [?x :q ?m]))`, and the test asserts its five tuples on both planner paths. The alternative is a per-group filter with no outputs as `or-join`'s job alone. It is excluded, because the two forms keep the same tuples, and the fallback evaluates a later branch only for the tuples the earlier branches left unanswered (§4.2). `Validate` refuses an empty header and a required run that overlaps the outputs, and nothing else about the header's shape.

### 2.2 A required variable the environment alone binds

A required variable that only a query input binds is legal for every form. The run carries the input's value in every tuple (`NESTED_SCOPES_AS_QUERIES.md` §5.4). A header of such variables alone has the environment's one tuple as its run and the unit relation as its subject. For `or-join` and `or-default-join` the branches read it as they read any required variable. For `not-join`, and for the `not` that infers to it, the body runs over that one tuple and decides the whole scope. A body with a result empties every group, and a body with none leaves them. That is Datomic's `not-join` with its variables bound by `:in`. A header of such variables shares no data variable with the scope, and that is not a defect of the query. The inference writes this header for a headerless `not` reading only an input, `[?e :entity/kind "thing"] (not [?x :entity/flag ?flag])`. So a refusal of the header would refuse that `not` with a message about a form its author never wrote, against goal 6.

### 2.3 Refusals

§2.4 of `NESTED_SCOPES_AS_QUERIES.md` stands. Each refusal names the form, the variable and the repair. Where a branch is at fault it names the branch by its position, counted from one. The header checks run at every boundary through one function: under the rule set at `Prepare`, and with none at the text boundaries (§6).

The refusal of a variable a branch reads, which neither the branch nor the header binds, is one where a branch is at fault. So it names the branch by its position. Its repair is binding the variable in the branch or naming it in the header. The alternative is the form and the variable alone. That leaves the author of a form with several branches to find the one at fault by reading each.

The refusal of a required run no order binds has two cases with two repairs. In the first, no input and no clause binds the variable, and the repair is binding it. In the second, some clause binds the variable, but no order places that clause before the form. Two forms that each bind, in one branch, a variable nothing else binds are that case, and the repair is the order. One computation tells the two apart on both planner paths: `query.NewNoOrderError` (`datalog/query/clause_ready.go`). `orderClausesForCompile` (`datalog/algebra/compile_order.go`) and `createPhasesGreedy` (`datalog/planner/clause_phasing.go`) each return it at their stall. It names every clause left unplaced, with the variables it waits on. It appends "(no input or clause binds it)" to a variable with no input and no provider, and nothing to one with a provider. A clause waiting on no variable, which the planner's gates alone produce, is named as such. `Prepare` leaves this refusal to the planner (`NESTED_SCOPES_AS_QUERIES.md` §5.1), and goal 5 binds the two paths to one message for one text. Two alternatives are excluded. One message saying that nothing binds the variable is false in the second case. A message per path, each stall rendering its own, refuses one text with two messages, and it lets the planner's message say of a provided variable that nothing binds it.

A refusal the planner raises names the prepared form, with the header the inference wrote. A header's provenance is not a fact the engine holds (`NESTED_SCOPES_AS_QUERIES.md` §5.3). So the alternative, naming the written headerless form, has no input past `Prepare`. The header in the message is the inference's decision shown to the author, beside `Explain`, which plans the prepared query (`NESTED_SCOPES_AS_QUERIES.md` §5.1). `TestExplain_PlansThePreparedQuery` is its test. Every scope of the prepared query is planned at `PlanQuery` (§4.1), so `Explain` refuses a branch no order runs as `Query` does, on both planner paths, with the one message. `TestExplain_RefusesABranchNoOrderRunsAsQueryDoes` and `TestPlanQuery_RefusesABranchNoOrderRunsOnBothPaths` are its tests. Every rule body the query's invocations run is planned there too (§4.1), so `Query`, `Explain` and `ExplainAlgebra` refuse a body no order runs with the one message, at any depth of invocation and with the stall inside a form or an inner query of the body, and accept the same text. `TestExplain_RefusesARuleBodyAsQueryDoes`, `TestExplain_AcceptsARuleBodyAsQueryDoes` and `TestPlanQuery_RefusesARuleBodyNoOrderRunsOnBothPaths` are its tests. The refusals `InferHeaders` itself raises name the written form, since they are raised on it.

## 3. The find boundary

One rule serves both find kinds: the relation the find runs over is the product of every group that reaches the boundary, the groups the find does not read included. A product with an empty factor is empty, and a factor with tuples multiplies the rest. Goal 3 of `NESTED_SCOPES_AS_QUERIES.md` ranks one rule for both find kinds over two, and `DefaultQueryExecutor.Execute` (`datalog/executor/query_executor.go`) is the boundary.

Under a projection find the boundary answers the product's projection without forming the product. With set semantics, the projection of a product onto one factor's symbols is that factor when the other factor is non-empty, and empty otherwise. So a group the find does not read is an existence verdict. A group with no tuple empties the result. A group with a tuple leaves the others as they are. The verdict is taken by one pull of the group's iterator, and an iterator filling a replay cache is read to its end before it is closed. The groups the find reads are returned as the group holding every find symbol, or as the product of the groups that together hold them. A sort key that is a collection or relation input symbol no clause of the `:where` binds orders that product, since the input's group is a factor of it, and the projection onto the `:find` symbols drops the key after the sort (`validateOrderBy`, `datalog/query/validate.go`). A sort key bound nowhere is refused.

Under an aggregating find the boundary forms the product and aggregates over it. The projection identity holds for a projection and not for a count: a count over the product counts every tuple of it, so an unread factor with two tuples doubles the count where it leaves a projection unchanged. The aggregate is taken over the whole join, grouped by the find's variables (`NESTED_SCOPES_AS_QUERIES.md` §2.5), and a sort key under an aggregating find is a group key alone. The planner keeps every symbol of the join to the boundary under an aggregating find, what each top-level clause provides and what each collection or relation input binds (`terminalSymbols`, `datalog/planner/phase_contract.go`). `InsertJoinProjects` (`datalog/algebra/rewrite_project.go`), the algebra path's join-project insertion, narrows a join's child to the symbols live above it, which begin as that same set, so it projects none of them away. A kept set that dropped a symbol would collapse, before the aggregate counted them, the tuples that differ in it alone. The framed aggregating subquery of §4.4 reaches its boundary as one group: an inner query whose body reads no input is aggregated once and paired with every run tuple.

Three alternatives are excluded, each by the failure it produces. The first is a projection that returns the one group holding every find symbol and discards the rest. Under it a `:where` holding a pattern no tuple matches, sharing no symbol with the find, answers the other group's tuples, where a conjunction holding an empty relation is empty. The second is a refusal of more than one group under aggregation, an unread data group included. Under it the same `:where` is refused as disjoint relations whether or not the unread group holds a tuple. That refusal records a mechanism's limitation, which goal 6 says is not an error about the query. The third is the existence verdict under an aggregating find, the projection find's rule applied to both kinds. Under it `[:find (count ?x) :in $ [?x ...] :where [?e :r ?n]]` counts the input's group alone, while the same query with the input spelled as a ground, `[(ground [#id "e16"]) [?x ...]]`, extends the pattern's group and counts the product, where `NESTED_SCOPES_AS_QUERIES.md` §2.5 makes the two spellings one relation with one answer.

## 4. The executor

### 4.1 One primitive

A scope is a header and a clause list. Each branch of an `or-join` or `or-default-join` is a scope under the form's header. A `not-join` body is a scope under its all-required header. A subquery's inner query is a scope under its `:find`, with its `:in` as the header's required run.

The primitive has two operations. The first is the planner's and the second is the executor's.

- `plan(scope)` is the planner's `PlanScope`.
  - It frames the scope as the query `[:find <header> :in $ % :where (scope/required <required run>) <clauses>]` and plans it under the rule set.
  - The scope is the planner's value, a header and a clause list, and the executor frames no query of its own.
  - The text carries the binding, and the scope is planned under no bound symbol. So the plan is cached under the text alone and made once per distinct scope text (`NESTED_SCOPES_AS_QUERIES.md` §5.2).
  - `PlanQuery` frames every form of the prepared query, an `or-join`, an `or-default-join`, a `not-join` or a subquery, through `Framing.Branches` and `ReadSubqueryFrame` (`datalog/planner/framing.go`), and plans each frame through `PlanScope` (`planFormScopes`, `datalog/planner/scope_planning.go`).
  - A form inside a branch is planned when the branch's scope is planned, since `PlanScope` plans through `Plan`, which walks the scope's own phases. So a branch no order runs is refused at `PlanQuery` on both planner paths, and `Explain` refuses it as `Query` does (§2.3).
  - The executor frames the same form from the groups in hand and reads each frame's plan from the cache.
  - A frame's symbols stand in the header's order, the required run then the carried outputs, never the subject's. So a frame's text is a function of the text and of which header symbols are bound before the form, which the planner reads from the phases and the executor from the groups.
  - A data pattern and a bound invocation over a streaming group (§4.4) are framed as window scopes, one clause under the required run of its symbols bound before it, through `planner.WindowFraming`, which the walk at `PlanQuery` and the executor's two routes read alike.
  - Whether a group reports no size is a run-time fact the plan cannot see, so the walk plans the window scope of every clause that can window: a data pattern, or an invocation derived at its clause, that stands after a clause of its scope other than `scope/required` and shares a symbol bound before it. The cost is a plan per such clause whose group is held at run time, once per database per text.
  - So executing a planned query plans nothing, and `Explain` accounts for every plan a run reads (`EXECUTION_PLANS_NOTHING_PROOF.md`).
  - The alternative to planning the window scopes at `PlanQuery` is the two routes planning at the handler, under which `Explain` accounts for less than a run plans.
  - The alternative to planning the forms at `PlanQuery` is the executor planning each scope where it first frames it. Under it the physical path's `PlanQuery` and `Explain` accept a text whose branch no order runs, which the algebra path refuses at `algebra.Compile`, so one text has two verdicts by path at `Explain`, against goal 5. And a frame whose symbols follow the subject's order plans one branch under two texts when the subject's layout differs between two runs of the enclosing query.
  - The planner leads with `(scope/required …)`, and no rule set declares into `scope`. The readers of the `scope` kind are `RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §1.1's.
  - One reader wants a scope's clauses in the planner's order and runs nothing: the magic rewrite (`NESTED_SCOPES_AS_QUERIES.md` §5.5). It reads the scope's plan as the planner made it, the phases' clauses in phase order less the `scope/required` invocation that opens them.
  - Which passes a plan runs is the planner's decision. The alternative is the reader planning the scope under passes of its own choosing. That puts the decision in the reader, which the paragraph below excludes.
- `run(plan, run)` executes the plan with `run`, a relation carrying the required run's symbols by name. The run is held under `scope/required` in a context that carries every relation the enclosing context holds, with `scope/required` rebound to this scope's run, and no environment. `(scope/required …)` binds each required symbol by finding it in the run's own symbols, never by its place in the run's layout. A run lacking a required symbol is the query's error. The operation returns a relation of the header's symbols, by name. The alternative is the run read by position against the required list. That is correct only while one list builds both sides, and nothing checks it. A run laid out otherwise binds each value to the wrong variable and returns tuples, not an error.

The bodies the query's invocations run are planned at `PlanQuery` too (`planInvocation`, `datalog/planner/scope_planning.go`, over `datalog/planner/rule_bodies.go`), one computation the executor's evaluation reads:

- For each invocation of the prepared query, at the top level and inside every scope the walk plans, the set it evaluates: the set as given for a free invocation of a predicate reaching no required predicate, and the rewrite otherwise (`EvaluatedSet`).
- The strata that set runs for the predicate (`NeededStrata`).
- Each stratum's bodies, the plain, delta and lower copies, each planned as the query finding the rule's head (`PlanStratum`).
- A body is planned with the fixpoint's predicates held (`query.HeldByFixpoint`). Inside it an invocation of a predicate without required positions reads the fixpoint's relation and plans nothing, and one of a predicate with required positions is derived at its clause, its bodies planned the same way.
- The rewrite plans the scopes it reads for their order with every invocation held (`query.HeldEvery`), since it decides each site itself.
- Which invocations are held is part of a plan's key, beside the query, the rule set, the bound symbols and the options (`NESTED_SCOPES_AS_QUERIES.md` §5.2).
- The plan carries each invocation's evaluation by its clause (`PlanEvaluation`, `RealizedPlan.Evaluations`): the positions bound before it, the set it evaluates, whether that set is a rewrite, and each needed stratum with its planned bodies. The executor's evaluation reads it from the plan being run, through the clause executor built for that run (`DefaultQueryExecutor.plan`), and runs each scope inside a body under the same held value, so executing a planned query plans no body and rewrites no set, and `Query`, `Explain` and `ExplainAlgebra` refuse a body no order runs alike (§2.3). The magic-sets event reports the rewrite the record states, so a plan the cache serves under a set equal to the one it was made under reports what that run's evaluation makes and nothing else.
- The alternative is the bodies planned at evaluation alone. Under it `Explain` and `ExplainAlgebra` accept a body `Query` refuses, at any depth of invocation, against goal 5, and the executor plans at evaluation what the planner did not, a second computation of which bodies a query runs.

The planner is the one orderer. No clause of a scope runs in written order. No loop beside the planner orders a branch's clauses. No reader of a scope's order builds a planner of its own. The alternative is a loop that runs a branch's clauses in written order. Under it an expression written before its binder is skipped, since `executeExpression` returns the groups unchanged when no group carries the expression's symbols. The branch of the query §2.1 quotes then runs without its expression. It answers the five tuples only because that expression binds a local nothing reads, and a tuple holding a nil value reaching the fallback's tuple key then panics the clause-based path.

### 4.2 The window

A branch's result for a subject tuple is a function of that tuple's projection onto the required run, by `NESTED_SCOPES_AS_QUERIES.md` §2.2, at every depth. A nested form reads its own header. A subquery reads its inputs. A flat-header fallback inside a branch reads nothing of the branch. On the primitive that fact is an identity. For a run X over the required run, `run(plan, X)` is the projection onto the header of X joined with the branch's clauses. Join distributes over union, so `run(plan, X ∪ Y) = run(plan, X) ∪ run(plan, Y)`. Every clause the language admits inside a branch denotes a relation: a pattern, a predicate, an expression, a nested form over its header, a subquery framed as §4.4 frames it, and an invocation, whose rewrite seeded by X derives the selection of its predicate to X. The one shape that would break the identity, an aggregate over the run itself, has no spelling, since a branch's find is its header. So every partition of the distinct required run into batches answers the same tuples, provided the fallback decision reads a branch's result for the run tuple before the join on the carried outputs filters it (§4.3). A batch of one tuple is per-tuple evaluation. The whole run is one cached branch over it. Every batch size between them is as correct. A clause of a branch that binds a symbol the run binds unifies with it (`align.apply` in `datalog/executor/relation_ops.go`). So a result tuple carries its own run tuple on the required run, and the join on the header symbols both carry pairs it with that run tuple's subject tuples alone. What differs between batch sizes is cost and what is held. The plan's machinery is paid once per batch: the hash join collapsing the held run with the pattern's result, the projection of the held run for `scope/required`, the materialized relations, the context derivation and the verdict. The matcher's work is paid per key either way, at or below the boundary of §4.6. The subject tuples held are the batch's.

The executor runs every branch over a window of the subject. Every subject, whether or not it reports a size, is read into windows of one tuple, then two, doubling to the cap. Each window holds its tuples and nothing of the subject beyond them. So the subject is read once, and the first result follows one pull. The window's workspace grows with the window, by the same doubling, and never past the cap. So a result abandoned after its first tuples has paid for the windows read and nothing more. Two such results are the one the find boundary pulls once for its verdict (§3) and one read under a limit. The cap and the growth are options on `ExecutorOptions`, since the janus `CLAUDE.md` excludes a package-level setting. The cap's default is the matcher's boundary of §4.6. Two alternatives are excluded. A workspace allocated at the subject's size when it reports one, with the subject run as one window, reads every key of the subject before the first result, which an abandoned result pays for nothing. Growth without a cap holds about half the subject in its last window and allocates a larger workspace at every window. The cap bounds both.

Per window:

- The window's tuples are projected onto the required run. Under the union the projection also carries the outputs the subject carries (§4.4).
- The keys the kept index of §4.6 already answers are left out.
- Each branch's plan runs once over the keys that remain, through `run`.
- The results are indexed.
- Each window tuple probes the index. The projection and the carried-output filters of §4.3 apply per tuple, as they applied per subject tuple.
- Under the fallback a later branch runs over the keys the earlier branches left unanswered in the window. So no branch is evaluated for a key an earlier branch answered, and the hold before a window's first result is the window.

Some branches read nothing of what they are given. What a branch is given is the required run under the fallback, and the required run with the carried outputs under the union. A branch reads a given symbol when a data pattern of the branch mentions it or any clause of the branch consumes it, whether or not another clause provides it, since a clause binding a run symbol unifies with it (`BranchReads` in `datalog/planner/framing.go`, which the planner's walk and the executor's framing read alike). A branch whose clauses only provide a given symbol does not read it. A branch reading no given symbol has as its run the environment's tuple over the required symbols the environment alone binds, or the unit relation when there are none. That is one window with nothing of the subject in it, and its result is probed with no key. A lone ground binding an output the branch is not given is such a branch, and so is an uncorrelated subquery with no input binding none, a decorrelated subquery binding the required run among them, built once for the form. A form given nothing runs every branch once over the unit relation. Two alternatives are excluded. The first reads a given symbol only when a clause consumes it that no clause of the branch provides, or a data pattern mentions it. Under it a branch whose clauses each provide the symbol another consumes, `[(identity ?e) ?w] [(identity ?w) ?e]` over a header of both, reads nothing, is framed over no run, and is refused as unorderable in every form, where the language answers it. The second reads a given symbol any clause mentions, providing it or consuming it. Under it a branch that only provides a given symbol is rebuilt per window: the four decorrelated subqueries of `TestComplexQuerySubqueryExecutionCounts` (`datalog/storage/optimization_matrix_test.go`), each binding the scenario and an aggregate over every task, are built once per window of the ten scenarios, and the test's count of four builds reads sixteen, which undoes what decorrelation buys.

A branch holding an invocation runs over the window as any branch does, and its fixpoint is continued across windows. The sets of every stratum, the whole predicates' relations and the derived-tuple count are carried from window to window. A window's keys enter the seed predicate's stratum as a delta, and the strata re-run from the lowest one that changed. The result is one fixpoint over the whole run. The seed decides which keys the adorned predicates carry, and never what a key carries. That is the magic-set correctness the rewrite rests on (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §1.3). Every read of an adorned predicate inside a body is at a key whose magic fact the same window derives from the body's own guard. An invocation under a non-monotone form is adorned only where its adorned predicate lies in a stratum below the rule's own, and is left unadorned otherwise (`NON_MONOTONE_FORMS_PROOF.md` T6). A same-stratum invocation stands only where evaluation is monotone (`NESTED_SCOPES_AS_QUERIES.md` §2.5). So each window's closure from the carried sets is the least fixpoint above them, and by induction over the windows and the strata it is the fixpoint over the keys seen so far. Each derivation fires in exactly one window when the semi-naive delta copies cover every occurrence of a predicate that changed in the window, the lower strata included. A body with no same-stratum invocation gains a marked copy per lower-stratum occurrence. That copy runs over the lower strata's new tuples at the window's iteration zero, in place of the whole view, and in the first window those new tuples are the whole lower relations. One rewrite serves every window, since the rewrite is a function of the predicate and the adornment. The iteration bound is counted per window per stratum. The tuple bound is counted over the carried count. The stratum's begin and complete events fire once per form execution, at the first window and the last. Every window reads the query's one snapshot. The alternative is a fixpoint per window seeded afresh. It re-derives every tuple a later window's seed reaches, which is the fixpoint per subject tuple goal 2 excludes, at the window's grain. So the zero-default count idiom with a rule inside its subquery, `(or-default [(q [:find (count ?r) :in $ % ?g :where (reaches ?g ?r)] $ % ?g) [?n ...]] [(ground 0) ?n])`, costs one rewrite and one stratum evaluation whatever the subject's size.

Two alternatives to the window are excluded. The first is a gate that returns at the first uncorrelated subquery without reading the clauses after it. It frames a branch whose later clause reads a required variable over no required run, and the planner then refuses that variable as unbound on both paths, where the language answers it. Under the window a branch's run is read from every clause, as above. The second is a batch size per form chosen by the kind of the branch's clauses: every `or-join` branch per tuple, and a cacheable `or-default-join` branch over the whole outer. That is the mechanism goal 9 names as no contract. The window is one evaluation whose only parameter is the batch.

Nothing materializes the subject. A subject of several groups is joined into one by a fold of the hash join under the groups' common symbols. Each group after the first is the build side, held in the join index under its key. The join so far is the probe side, streaming through it. So each group is opened once, the subject reports no size, and the subject itself is never held. Two groups sharing no symbol join under no key: every build tuple sits under one key, and every probe tuple is combined with each of them, which is their product. One group held per join is a bound, not a choice. A procedure emitting the product of two single-use relations, each read once, holds the whole of the one exhausted first, since the other's last tuple pairs with every tuple of it. With several groups it holds all but one. The build side is the group, never the join so far, so the fold holds the groups beyond the first and never their product. Three alternatives are excluded. Every group materialized and joined by a fold over the materialized groups holds every group and delays the subject's first tuple until every group is read. A product reopening its inner side per outer tuple opens a single-use group, a form's result among them, a second time. A lazy sequence over the inner side holds that group as cells, walks them once per outer tuple, and wraps a streaming relation alone, so a form's result as the inner side is reopened the same way.

### 4.3 `OrFallbackRelation`

`OrFallbackRelation`, the form's result (§4.8), and `OrFallbackIterator`, its iterator, are the executor's evaluation of the two branch forms over the window. The type carries the contracts §7 names, by the names of its internals. The alternative is a new type carrying the same contracts, whose cost is retargeting every test that asserts them. `OrFallbackRelation`:

- iterates its subject lazily and reports no size
- runs each branch once per window through `run`, and probes the window's index per subject tuple
- projects a branch tuple onto the subject's symbols and the header's outputs, filling the gaps from the subject tuple
- joins an output the subject carries by keeping only the branch tuples that agree with the subject's value, and never supersedes it (`NESTED_SCOPES_AS_QUERIES.md` §2.3)
- joins an output the environment binds with the environment's tuple
- deduplicates its branches' answers under the union when the form has more than one branch, on the composite key the derived properties (§4.7) give, since two branches can answer one subject tuple and no property says otherwise. Under the fallback it deduplicates only when the subject carries no key, since one branch answers each subject tuple and a branch's answer is a set, and a set-preserving operator does not deduplicate again (the relational invariants of the janus `CLAUDE.md`).
- frames its branches at construction and reads each frame's plan, made at `PlanQuery` and served from the cache (§4.1), so a branch's planning refusal is `PlanQuery`'s error, whatever the subject holds, and surfaces a subject scan failure and a branch's execution failure when the result is driven, never as no match
- copies a tuple at the boundary when its source reuses its workspace
- keeps the branch cache across windows, under either form (§4.6)
- takes the fallback decision for a run tuple on the branch's result for that tuple, before any filter on the carried outputs. The alternative is filtering a correlated branch's result against the outer tuple before deciding whether the branch answered. That changes the decision, since an output bound into a branch before a non-monotone decision changes it, the third example of `NESTED_SCOPES_AS_QUERIES.md` §2.3. So the decision reads the branch's result first, and the join on the carried outputs follows.
- decides what a branch sees per branch:
  - Under the fallback a branch sees the required run alone. So an invocation in it is seeded by the header (§4.5), and the carried outputs the subject carries are joined with its result after the decision (§4.6).
  - Under the union a branch holding an invocation sees the required run alone. The invocation is seeded by the header, and the carried outputs are joined with its result through the index's key.
  - Under the union a branch holding no invocation runs over the window's projection onto the required run and the carried outputs, its seek, after its plan over the required run alone is accepted (§4.4).
  - An output the environment alone binds is joined with the environment's tuple by the carried-output filter after the probe, under both forms.
  - The alternative is one set of visible symbols for every branch of the form, the required run with every carried output. That seeds an invocation inside a branch at a position the header does not name, which §4.5 excludes.

The evaluation is four modules every windowed form shares and a policy per form. That is the decomposition `OR_FALLBACK_RELATION_PROOF.md` derives. Each module is one lemma of that proof, reads nothing of the form, and has the lemma's tests:

- **The window reader** (the proof's L1) reads the subject's iterator into the windows of §4.2. It yields each window with its ordinal, reports the subject's exhaustion, copies a tuple whose source reuses its workspace, and surfaces the subject's failure. It owns the subject-tuple, exhaustion and window events of §4.9.
- **The frames** (L2) are one frame per distinct required list among the branches' plans, each resolved against the subject's symbols and the environment's tuple. A frame's run over a window is the window's distinct keys less those an earlier window ran. A frame of no subject symbol runs once, over the environment's tuple or the unit relation.
- **The kept branch** (L3a, L3b) is the branch cache of §4.6 over a branch's result symbols, keyed on the header symbols the subject carries. It is built from a plan and a run through `run` and read whole, grown by every window's build, and probed per window tuple. The EA arm of §4.6 is a second build under its own conditions. It owns the build event of §4.9.
- **The continuations** (L6) are the evaluations the branches' invocations continue across windows. The outermost windowed form's iterator owns them, and every form inside it shares them.

A form composes them. A window is read. Each frame's run is computed. Each branch is built over its run. Each window tuple is answered by probing the built branches. The form's own policy has five parts:

- the framing of its branches (`planBranches`, over `planner.GivenSymbols` and `planner.Framing.Branches`, the one computation the planner's walk at `PlanQuery` reads too): the union's seek and its plan over the required run alone, the fallback's required run alone, the `not-join`'s all-required header over one body, and the subquery's inputs with its find shape (§4.4)
- the emit rule: every branch's matches under the union, the first branch's under the fallback, the window tuple with no match under the `not-join`, and the one body's matches under the subquery. The three forms with outputs share the carried-output filter and the output projection.
- the fallback's window step (§4.10): the prefetch of a window's entities above the threshold, under the option, applied to the window as read, before any frame's run is computed
- the fallback's narrowing of a branch's run to the keys the earlier branches left unanswered, and its record of the keys a build answered (L3c), applied between the frame's run and the build
- the deduplication rule of the bullet above and the properties of §4.7

Two alternatives are excluded. One relation with a mode per form puts the subquery's framing seams and the fallback's answered keys inside the one loop. There a defect in the shared part reaches every form, a green test of one mode can mask another's, and a `not-join` or a subquery is reported under the fallback's names. A relation per form, each carrying the window, writes the window reader, the frames, the kept index and the continuation ownership once per form. The proof's F1 names which lemmas read the form, and the split follows that line.

The relation reads the header and computes no interface from what it holds (`NESTED_SCOPES_AS_QUERIES.md` §4):

- The branch's visible symbols are the required run. Under the fallback form an output the subject carries is joined after the branch runs, never bound into it, since an output bound in before the decision changes the decision. Under the union a branch holding no invocation binds it as its seek, and a branch holding one has it joined through the index's key, as §4.4 states.
- The relation's schema is the subject's symbols plus the header's outputs. A local every branch binds is not in it.
- The symbols a branch's indexed result is joined with the subject on are the header symbols both carry: the required run, and under the union the carried outputs.
- The environment contributes a required symbol only when no group binds it.
- A required variable the environment alone binds narrows a branch's run as any required variable does.
- The projection's combination sites filter on the outputs the subject carries and let no branch value supersede one. Those sites are `projectionPlan.project` and `agreeing` of `matchEmit`, the drain `emitCachedMatches` begins, and the EA-built branch.
- A branch's run is the window of §4.2, never a size read from whether the form has join symbols.
- The branch cache is keyed on the header symbols the subject carries, never on every subject symbol a branch shares. A form with an empty required run has the unit relation as its subject.
- A required variable the environment binds is legal (§2.2), and no refusal reads a required variable no group binds.

### 4.4 The handlers

- **`or-join`.**
  - The subject is the groups holding a header symbol: one group unmaterialized, or several joined into one.
  - A branch holding no invocation is planned first over the required run alone, the language's scope. That plan's refusal is the form's, naming the branch counted from one on both planner paths. The alternative is a plan with the carried outputs bound from the start. It runs a branch the language refuses: the cycle of two identities under a header that binds none of it.
  - Such a branch then runs over the window's projection onto the required run and the carried outputs, its seek. For a monotone branch the seek answers the same tuples as binding the required run alone and joining the outputs after, since an output another clause binds is joined (`NESTED_SCOPES_AS_QUERIES.md` §2.3). The alternative is the run over the required run alone with the join after. It loses the seek on the subject's values that §7 names for a flat `or-join`.
  - A branch holding an invocation runs over the window's projection onto the required run alone. Its result is joined with the window's tuples on the required run and the carried outputs, through the index (§4.6).
  - With no group holding a header symbol, the subject is the unit relation. Each branch runs once over it, and the union joins at the collapse as a new group.
  - The result replaces the consumed groups (§4.8). It carries the subject's symbols and the outputs.
  - `OrClauseComplete`'s `semantics` is `"union"` when the subject is the unit relation and `"correlated-union"` otherwise. The header decides that fact. The handler emits the or-clause events for every `or-join`, written or inferred (§4.9).
- **`or-default-join`.** The same `OrFallbackRelation` with short-circuit. Per key of the window, the first branch with a result answers, and a later branch runs over the keys the earlier branches left unanswered (§4.2). The subject is the groups holding the required run. The carried outputs are filtered after the decision, since an output bound into a branch before a non-monotone decision would change the decision.
- **`not-join`.**
  - The subject is the groups holding a header symbol.
  - The body is one branch under the all-required header, composed over the modules of §4.3. Its frame's run per window is the window's distinct projection onto the header variables the subject carries, less the keys an earlier window ran. The body is built over that run. A window tuple whose probe returns nothing is yielded, and one whose probe returns a tuple is dropped.
  - The result is the subject's tuples with no match, in the subject's order. So it keeps the subject's keys and ordering, and it replaces the consumed groups (§4.8).
  - The subject is read once, and nothing of it is held beyond the window.
  - A header variable the environment alone binds is a constant on both sides and is no key.
  - A header the environment alone binds has the environment's one tuple as its run and the unit relation as its subject. The body is built once over that tuple. The unit relation's one tuple is dropped when the body has a result and kept when it has none. The find boundary's verdict of §3 then empties the result or leaves it (§2.2).
  - An empty subject yields no window, builds nothing and yields nothing, which is the subject's own answer.
  - A failure of the body's scan is the form's error, surfacing when the result is driven.
  - The body is never run per combination. One run per window, with the fixpoint of an invocation in the body continued across windows, is what keeps that invocation at one evaluation (goal 2).
- **Subquery.**
  - The inner query is one branch composed over the modules of §4.3, under §4.2's window over the relation of its argument combinations. The subject is the groups holding an input symbol, joined into one. The branch is framed over the data inputs as its required run, with the binding symbols as its outputs. Its frame's run per window is the window's distinct projection onto the inputs, less the keys an earlier window ran. The body is built over that run, and each window tuple's matches are yielded joined with the tuple. A repeated combination reads the kept branch and is not run again.
  - The call's substitution is the frame's own, read once from the text by `planner.ReadSubqueryFrame`, which gives the planner's walk at `PlanQuery` and the executor's framing one reading of the call: the inner symbols, a collection input's holder among them, the opening identity binding the members from it, the inner clauses under the call's sources, and the substitution. Each inner `:in` symbol stands for the argument at its place, and each inner `:find` element stands for the binding variable at its place. That is the unification `NESTED_SCOPES_AS_QUERIES.md` §5.5 states. The frame presents the run under the inner `:in` symbols, each found in the subject by the enclosing variable it stands for, and a constant argument's symbol by none: it takes the call's constant from the frames' environment relation, whatever symbol of its own name the subject carries. The planner's walk and the executor's framing read that standing from the one frame (`StandsFor`) and compute the carried symbols from it through one function (`Framing.CarriedBy`), so the two frame one call alike and executing an explained query plans nothing. The scope is the inner query as written, its variables renamed apart from the enclosing scope's. Its sources are renamed by the call's source arguments: a data pattern on an inner `:in` source, the `$` of an omitted or declared `:in` included, names the source the call passes at that place, and a nested call passing that inner source passes the call's, at any depth (`query.RenameSources`). The alternative is the inner clauses framed with their sources as written. Under it a pattern on a named inner source is routed by its own symbol and refused as an unknown source, and a pattern on the inner `$` reads the enclosing default source whatever source the call passed. The answer enters the kept branch under the enclosing names through `Relation`'s rename by symbol. An inner symbol written at an `:in` place and at a `:find` place stands for two enclosing names, the argument's and the binding's. Its attribute is copied under the binding's name through the identity expression, since a rename gives an attribute one name and the kept branch's key reads the argument's. So the probe, the carried-output filter and the emit, shared with the branch forms, read the enclosing names only, and the subquery's policy is its framing and nothing else of its own. The alternative is a rename inside the emit by position, against a find the frame composed. That holds only while the composed list and the answer's layout agree, and nothing checks it.
  - An aggregating inner query whose body reads an input is framed with its inputs as group keys.
  - One whose body reads no input is a pure aggregate. It is the frame of no subject symbol, built once at the first window and probed with no key. So it is aggregated once and paired with every run tuple, since adding group keys to a pure aggregate changes its kind (the janus `CLAUDE.md`, "Decorrelation Pure Aggregation Bug").
  - The binding names the inner query's outputs in the enclosing scope. The result enters the scope as the relation over them, joined with the run. A binding asserts nothing about cardinality. The alternative is a one-tuple check under a tuple or scalar binding. That is a count over the result that the binding's spelling hides: an aggregate the inner `:find` does not show, non-monotone where the inner query reads the rule's own stratum, and taken only with the run grouped. A count is written in the inner `:find` as one.
  - A binding symbol the scope already binds is a carried output. The carried-output filter joins it with the result after the probe. It is never bound into the inner query, whose inputs are its `:in` alone (`NESTED_SCOPES_AS_QUERIES.md` §2.5). Bound in before an aggregating inner query runs, it would change the aggregate.
  - A name written at two places of the binding unifies the two outputs it names (`NESTED_SCOPES_AS_QUERIES.md` §2.5). The presentation selects the tuples whose two outputs are equal and renames them to the one name, as an invocation's repeated argument selects on equality. The alternative is the later find element dropped at the presentation. That keeps a tuple whose outputs differ, with one value lost.
  - A keyword that reaches an attribute position through an input is evaluated as data. The pattern seeks the attribute, and an entity that lacks it yields no datom, which a fallback form answers.
  - An entity carries any attribute. The schema declares nothing about which attributes an entity may carry.
  - The refusal of an attribute the query names is an option decided at entry (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §4), never a rule of evaluation.
  - A scalar or tuple input is a position of the run, and a relation input is one position per symbol, each bound from the argument at its place (`query.InputPositions`).
  - A collection input is one position of the run holding the whole value, under the name `query.ScopeInput` mints for the position, `?scope/input.2`. The scope's clauses open by binding the members from it, `[(identity ?scope/input.2) [?n ...]]`, so the members join the body as a group inside the scope, and an aggregating inner find answers over all of them per run tuple. An invocation in the body is seeded from that group. The alternative is the members expanded into the frame's key, one run tuple per member. Under it an aggregating inner find answers per member and the members' answers are merged as a set, where the same query unnested answers once over all of them, and a member named twice builds the branch over a run holding one key twice (`RELATION_INPUT_PROOF.md` T3).
  - Inside a branch the combination relation is the branch's window (§4.2).
- **A data pattern over a streaming group.**
  - The pattern is one body under the header of the variables it shares with the group, composed over the modules of §4.3 under the subquery's emit rule.
  - The subject is the groups holding a shared variable, joined into one.
  - The body is built once per window over the window's distinct keys less those an earlier window ran, each key sought by the matcher (§4.6).
  - Each window tuple is answered with its matches joined, the pattern's other variables as the outputs.
  - Its frame is the window scope the walk at `PlanQuery` planned for the pattern, read from the cache (§4.1).
  - The result stands in the consumed groups' place (§4.8), reports no size, and reads the subject once.
  - Its keys survive when the pattern answers at most one tuple per subject tuple (§4.7).
  - A group held in memory binds the pattern through the matcher, which reads it as bindings and joins the matches at the collapse, since nothing is copied to read it twice.
  - The alternative is the matcher's bindings over a copy of the streaming group, joined back at the collapse. §4.2 excludes it: the copy is read once and discarded, and the collapse opens the consumed original a second time.
- **A bound invocation at the top level.**
  - The invocation is one branch under the header of its bound variables as the required run and its free variables as the outputs, run as the union form (§4.3).
  - The subject is the groups binding its arguments, joined into one.
  - The branch runs over each window's projection onto the required run. Its fixpoint is seeded by the window's keys and continued across windows (§4.2, §4.5).
  - Each window tuple is answered from the derived relation's index on the required run.
  - The result stands in the consumed groups' place (§4.8), reports no size, and reads the subject once.
  - The window is for an invocation that derives its predicate at the clause (§4.5) over a group that reports no size, as for a data pattern.
  - A group held in memory seeds the derivation through its projection onto the bound arguments and joins the result at the collapse, since nothing is copied to read it twice.
  - The run a frame holds per window is such a group, so the invocation a frame runs is seeded through the run and never windowed again.
  - Its frame is the window scope the walk at `PlanQuery` planned for the invocation, served from the cache under its text (§4.1), so its invocation clause is the object of the plan as first made, whichever framing made it.
  - That clause stands for the invocation the frame was planned for, and the form execution's continuations record the standing. A derivation at either clause continues the one evaluation.
  - So an invocation read through the window in one window and seeded through a held group in another, which a join whose build side is empty answers held, runs one rewrite and one evaluation (`INVOCATION_CONTINUATION_PROOF.md`).
  - An invocation of a predicate the scope holds has no fixpoint to seed. Such predicates are a stratum's relation, its last delta under the fixpoint, and the required run under `scope/required`. The invocation reads the held relation and joins it at the collapse, where the hash join holds the held relation and streams the group once. So it is never windowed, whatever binds its arguments.
  - An invocation binding nothing has the unit relation as its subject and runs once over it, the union joining at the collapse as a new group.
  - Two alternatives are excluded. The seed read from a streaming group materialized, with the collapse joining the group again, holds the group whole and reads it twice. The window taken on the group alone, held predicates included, runs a framed plan per window of a body's pattern result for the join the collapse makes, at every iteration of every stratum.
- **Rule bodies.** A body is planned by the planner's `PlanStratum` as the query finding the rule's head (§4.1), and the executor's stratum evaluation runs it on the primitive.

### 4.5 Rules inside scopes

An invocation inside a scope evaluates at its clause. It is seeded from the scope's bindings at that clause, the required run and what the planned clauses before it provide, once per scope execution. The branch holding it runs over the window's projection onto the required run alone (§4.3). So the seed is the header's binding, one window's keys at a time, and the fixpoint is continued across windows (§4.2). Inside a rule body the scope's context carries the stratum's held relations, so a same-stratum invocation reads the delta and never derives at the clause. The magic rewrite reads the scope's planned clauses as `NESTED_SCOPES_AS_QUERIES.md` §5.5 states.

### 4.6 The branch cache, the seek and the EA arm

A branch's window result is indexed on the header symbols its result shares with the subject: the required run, and under the union the carried outputs. The index is a `JoinIndex` the kept branch embeds (`cachedBranch`, `datalog/executor/kept_branch.go`). It is kept across windows and probed per subject tuple, and the probe returns the key's group with no allocation. A branch sharing none has an empty key, and its probe returns the whole result. A key a later window carries again probes the index and is not evaluated again. That is the discipline the fixpoint's sets apply to a repeated seed. Under the fallback the index is on the required run alone, since the decision reads the branch's answer for the required key before the carried outputs are joined (§4.3). `JoinIndex`'s contracts are these: one group per distinct key in the order added, the key read at the probing relation's positions, every tuple one group under no key, two keys under one hash told apart, a key added again joining its group, an identity matched by value, a probe allocating nothing, and `KeysUnique` as the candidate-key proof. Its tests are in `datalog/executor/join_index_test.go`. The index grows with the keys answered, a later window's tuples joining their keys' groups. The window's workspace is bounded by the cap, and the index is not.

The matcher's binding-driven scan narrows a scan to the bound value when the binding relation holds one distinct key. For several keys it leaves the bound at the pattern's constants, scans that extent once, and probes each datom against the keys (`matchWithHashJoin` in `datalog/storage/hash_join_matcher.go`). For a key at the entity position with the attribute constant, that extent is the attribute's. For a key at the attribute position with the other positions variable, it is the whole index. So a window of several keys on a large attribute reads the attribute, where per-tuple evaluation reads one narrowed scan per tuple. The matcher therefore has a per-key seek strategy beside the hash-join scan and the merge join. It makes one narrowed scan per distinct key, with the bound the one-key narrowing produces, and yields them as one datom stream. The hash-join iterator consumes that stream as it consumes the wide scan, so the join, the constraints, the CRDT resolution and the tuple building are unchanged. The strategy is chosen where the one-key narrowing is decided, after `buildHashSet` has counted the binding's distinct keys. At or below the boundary `chooseJoinStrategy` carries between a small binding set and a large one, the keys are sought one by one. Above it the hash-join scan and the merge join stand, and `chooseJoinStrategy` keeps reading the binding's `Size()` for the choice between them. A key at the attribute position is sought per key at any count, since the attribute is the prefix of its own index. A key the index cannot bind is a value that is not a reference at the value position, whose one-key bound is the pattern's own. It is probed against the one scan of the extent at any count, because a seek per such key would read the extent once per key, where one scan of it serves every key. The engine carries no statistic of an attribute's extent and estimates none. The keys in hand are the visible selectivity the planner's greedy ordering rests on (`docs/papers/STATISTICS_UNNECESSARY_PAPER_OUTLINE.md`). The seeks' cost is bounded by their count, and the extent's cost is a number the engine cannot see. The strategy reports one scan-funnel completion event of its own, named in `datalog/annotations/types.go` beside the hash-join and merge-join events, carrying the same funnel and the key count. The window's cap defaults to the same boundary, so a full window is sought per key.

One branch shape is built from the EA cache: one data pattern on the default source, whose entity position is a required variable the subject carries, with the attribute declared cardinality one and the matcher non-temporal. Those are the conditions the matcher's `CanFuseAttributeFetch` states for substituting a lookup for a scan, asked for the pattern's source (§4.7). Under `EnableEntityPrefetch` (§4.10) such a branch is built through `buildBranchFromEACache`: one `LookupAttribute` per distinct entity of the window, with the environment-bound value narrowing the result when that value is in the required run. The source condition holds because an entity lookup is the default source's answer, which the executor's attribute-fetch fusion already requires of the pattern it fuses. The built tuples are kept under the key of every run symbol the subject carries. So a required value the subject carries is compared at the probe, as the scan path compares it through the run. No warmth is read. §7 names the contract that the arm answers as the scan path does whatever the cache holds, with the value symbol required as with it free. The arm runs under the option that runs the prefetch, whose warm cache is the arm's benefit. So a query with the option off pays nothing for it (goal 7), and §8 measures the arm with the option on and off. A branch that fails a condition takes the matcher's path above.

### 4.7 Properties

`OrFallbackRelation` derives the result's properties through `orProperties`, from the subject's properties and the header:

- The outputs are what the branches produce, and nothing is overwritten, since an output the subject carries is joined and never superseded (§4.3). So no subject symbol drops its key or ordering on the branches' account.
- Whether every branch answers at most one tuple per subject tuple is judged against the header symbols the subject carries, the grain the result is produced at.
- That judgment reads properties. An expression binding one value answers at most one. So does a subquery whose find is aggregates and variables the subject carries, whatever its binding's spelling (§4.4). So does a data pattern whose entity position is a required symbol the subject carries, whose attribute is a constant, and whose attribute resolves to one value per entity under the handle. The matcher states that last fact through `CanFuseAttributeFetch`, which reads cardinality one and no `History`, the two facts §4.6 names, so the executor reconstructs neither. The capability takes the pattern's source, as `AttributeVocabulary` does, so a router answers from the source named. Two alternatives are excluded. A judgment by the kind of a clause alone never lets a data pattern answer at most one, so the subject's key is dropped through every pattern branch, and the union deduplicates on a composite key the properties do not require. The cardinality read from the schema in the executor omits the mode, so a pattern under `History` answers every version, and the key the result claims is false.
- A subject's ordering survives both forms. Its key survives under the fallback when every branch answers at most one tuple. Otherwise the result's key is the composite of the subject's key and the produced outputs. Under the union it is always the composite, since two branches can answer one subject tuple.
- The derivation emits `OrPropertiesDerived`.
- Every reader of the properties reads a result the `OrFallbackRelation` produces as it reads any relation. Those readers are the projection's dedup elision, the join's strategy and build side, and the scan-boundary restoration.
- A union over the unit relation (§4.4) is a new group with the full-header key and no ordering. No subject property reaches it.
- The `not-join` keeps its subject's properties, since it yields a subset of the subject's tuples in the subject's order (§4.4).

### 4.8 Group replacement and read-once

The form's result replaces the consumed groups through `replaceConsumedGroups`, with no join at the collapse, and emits `OrOuterReplaced`. A streaming subject is read once. The result stands in the subject's place, and a reader that needs the result twice materializes the result, never the subject.

### 4.9 The events

Every name in `datalog/annotations/types.go` whose fact this mechanism produces emits with the payload that file declares. The or-join handler emits `OrClauseBegin` and `OrClauseComplete`. The unit-run route emits `OrClauseUnion` and `OrClauseBranchComplete`. The derivation emits `OrPropertiesDerived`. The replacement emits `OrOuterReplaced`. The `OrFallbackRelation` emits `OrFallbackIteratorCreated`, `OrFallbackBranchNarrowed` and `OrFallbackBranchSuccess`. The modules of §4.3 report their own facts under every form. The window reader reports each subject tuple read, the subject's exhaustion, and each window with its ordinal, its tuple count and its distinct key count over the required run's symbols the subject carries. The kept branch reports each window's build with the branch, its symbols and the tuples built. Those four events are named in `datalog/annotations/types.go` for the module, under the `scope` family, and each carries the form it fired under. The alternative is the `or-fallback` names for them. That records a fallback under a `not-join` or a subquery that ran none, and a reader of `Analyze` cannot tell the form from the name. The handlers' own contract:

- The fallback handler emits its `OrFallbackRelation`'s events and no or-clause event.
- The completion event of a streaming form fires at construction with size -1, and a branch failure surfaces when the result is driven.
- A scope's run emits no `PhaseBegin` and no `PhaseComplete`. The form's own events report a branch's execution, and a phase event per window would be a handler call per window beside the window's own event.
- A stratum continued across windows emits `RulesStratumBegin` at the first window and `RulesStratumComplete` at the last. Its `RulesIteration` events number each window's iterations from zero (§4.2).
- §7's counts of branch executions read the kept branch's build events.

Preparation is a fact of its own. The executor's entry emits `QueryInvoked` with the query as received and `QueryPlanCreated` with the plan (`ExecuteWithRelations`, `datalog/executor/executor.go`), and `Prepare` runs between them. One event, named in `datalog/annotations/types.go` beside `QueryInvoked`, is emitted after `Prepare` under the same call-site guard. It carries the prepared query's rendering, whether the inference rewrote a form, and preparation's time. `InferHeaders` computes whether it rewrote a form when it returns the query it was given. A query with no handler pays nothing for it, as for `QueryInvoked` (goal 7). Two alternatives are excluded. The prepared text as a payload of `QueryPlanCreated` puts two facts under one name, where `Analyze` reads one fact per name, and it reports nothing when planning refuses the prepared query, since that event fires after planning. With no preparation event a handler sees what the inference wrote only by comparing the two renderings around it, neither of which is the prepared query, and `Analyze`, which sums latency per event name, attributes preparation's time to no event.

A plan made is a fact of its own. The planner emits `PlannerPlanMade`, named in `datalog/annotations/types.go` beside the query lifecycle's names, once per plan it makes, under the handler it plans with, carrying the query planned and the bindings the plan was made under, with planning's time as its latency. A plan the cache serves emits nothing, so a run of a query the planner has planned emits none (`EXECUTION_PLANS_NOTHING_PROOF.md` T7). `Explain` plans under no handler and emits none.

A handler sees every query the database's `Query` path is asked, once. The path resolves the query, opens the read session, validates the declared sources and converts the inputs before the executor's entry, and a refusal it raises at any of those steps is reported as the executor reports its own: `QueryInvoked` with the query as received, then `QueryComplete` carrying the error, with no preparation and no plan event (`queryUnderPlannerOptions`, `datalog/storage/convenience.go`). A query that does not resolve, text that does not parse or a value that is neither text nor a query, is reported invoked with a rendering of the value it was given, text as it was given. A query that reaches the executor's entry is reported there. The alternative is such a refusal returned with no event, under which a handler counting invocations and completions misses every query refused while its inputs are converted. `Explain` and `ExplainAlgebra` plan under no handler and report nothing on any path, so neither reports a refusal a handler would see without the plan it never sees. The lifecycle's payload keys, `KeyQuery`, `KeyRelationsCount`, `KeyTuplesCount` and `KeyError`, are declared beside the event names in `datalog/annotations/types.go`, since the executor's entry and the database's path both write them. `TestQuery_ARefusalReachesTheHandlerAsACompletedQuery` (`datalog/storage`) is the test.

## 6. Boundary parity

Every static check a query's text admits runs through one function, `query.ValidateQuery`, which `ParseQuery`, `qb.Build` and `Prepare` each call and run no check of their own beside: the non-empty `:find` and `:where`, the scalar find's shape, the input shapes (`%` declared at most once, and a tuple or relation input naming at least one variable, so `[]` is refused as the builder's `Tuple()` and a hand-built `TupleInput{}` are), the clause shapes, the rules-use rule and the `:order-by` rule. It reaches every inner query through `SubqueryPattern.Validate`, which runs it over the inner query whole and refuses an inner `:limit` and an inner pull, so one text is accepted or refused alike at every boundary and at every depth, with one message. The alternative is each boundary composing its own subset of the checks. Under it an inner `:in` declaring `%` twice passed every boundary, an inner invocation under an inner `:in` declaring no `%` passed `Prepare`, the inner `:limit` and pull refusals and the `:order-by` rule were the parser's alone, and the builder panicked at `Where` on an inner query's refusal.

Two checks are `Prepare`'s own and no text boundary's, since the text alone does not decide them. One is that every invocation names a predicate the rule set defines at its arity (`NESTED_SCOPES_AS_QUERIES.md` §5.1). The other is that no variable lies in a namespace the engine mints into, `unify`, `scope`, `magic`, `adorned` or `delta`: the same text is the engine's own when the engine wrote it, the prepared text carries `?unify/x.2` and `?scope/input.1`, and every phase the planner emits parses back through `ParseQuery`, so `ParseQuery` and `qb.Build` accept the spelling and `Prepare` refuses it as `EngineNamespaceError`, naming the variable, the namespace and the repair (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §1.1). `NewRuleSet` refuses a rule naming such a variable the same way.

The header checks run at `ParseQuery`, `qb.Build` and the executor's entry alike. They ask whether every branch binds every output and whether a body reads outside its header. `NESTED_SCOPES_AS_QUERIES.md` §5.5 states that fact and the alternative it excludes. One function computes them. It infers a written form's branches under the form's header and runs `checkHeader`. The `Validate` methods call it with no rule set. Under no rule set an invocation provides every variable argument, so a text boundary refuses a subset of what `Prepare` refuses, and never what the rule set would accept. `Prepare` calls it with the rule set. One message per fact carries the parts `NESTED_SCOPES_AS_QUERIES.md` §2.4 names: the form, the branch counted from one, the variable, the repair.

Goal 5 binds the builder and the renderer the same way. `qb.Build` accepts an inner query with no `:in`, as the parser does. A query's text is the query's own to render, where the query is held. So `Query.String` is the one renderer, and the parser carries none. `Query.String` renders a byte constant, an instant constant, a pattern's source and the scalar find's marker in the form the parser reads, so every phase the planner emits parses back.

Every constant renders through `query.FormatValueEDN`, the one renderer of values:

- A float's mantissa always carries a point, so a whole-valued float parses back as a float and never as an integer.
- A string is quoted at any depth of a vector.
- Every value `VectorElements` reads as a vector, a typed slice included, renders element by element.
- A database-function predicate and a transaction-range predicate render as the bracketed clauses the parser reads a predicate by.
- The plan cache keys a plan on the clauses' text, so the plan `[?e :a 5.0]` is served under is never served to `[?e :a 5]`.

The alternative is a renderer in the parser package. That puts the text of a value in the package that reads it, which the planner, the executor and the plan cache cannot reach. The copy that then stands beside it drifts: such a renderer dropped a pattern's source and rendered an instant through `%v`.
