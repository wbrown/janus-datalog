# Scope Execution and the Engine's Contracts

**Amends**: `NESTED_SCOPES_AS_QUERIES.md` §5.4 and §7. Its §1 to §5.3, §6 and §8 stand, except where a section below names them.

**Implements**: the rules and recursion of `RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §1 on the mechanism `NESTED_SCOPES_AS_QUERIES.md` corrects, with the executor contracts the merge-base `841caf8` carries kept on it.

**Baselines**: `841caf8` is the branch's merge-base with `main`, and `5b152c9`, the baseline `NESTED_SCOPES_AS_QUERIES.md` §6 names, is eight commits past it on the branch, `eacad7e` to `5b152c9`.

## 1. Goals

The goals of `NESTED_SCOPES_AS_QUERIES.md` §1 stand, and this design adds these.

1. Rules serve a caller at per-call cost: a query invoking a rule set runs on every call, at a cost the caller measures as its gate. The shapes: reachability as a recursive rule bound by every member of a collection input; readiness derived with stratified negation and a recursive propagation rule; and a loop in the caller's language replaced by one query over a rule set whose body holds an `or-join`, seeded by a collection input. §8 states the acceptance tests.
2. A bound invocation costs one rewrite and one evaluation that derives each tuple once, wherever the invocation stands, its seeds arriving as one relation or as the windows of §4.2 (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §1.3). The failure: an invocation under `not`, `not-join`, `or`, `or-join` or `or-default` reran the fixpoint once per outer combination, where one rewrite seeded by every bound value derives the same tuples once. A fixpoint per subject tuple is that shape again.
3. The overlay matcher of `RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §3.1 composes with `SourceRouter`, predicate pushdown and the EA cache unchanged. Every read path the executor takes is one the overlay covers, so a substitution of a cache lookup for a scan holds only under the conditions the matcher states for it.
4. The witnesses of `RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §2 record, per derived tuple, the rule and the body tuples of one derivation, the least of minimum depth, and `WhyNot` descends a rule's alternatives one at a time to the clause that produced no match. Their substrate is the scans of a planned query, which the witness rewrite extends with a fourth position bound to the matched datom's ElementID (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §2.1), and the fixpoint's record of each derived tuple's derivation (the same section, under Rules). Every scope in this design is planned through `QueryPlanner.PlanQuery` (§4.1).
5. One grammar (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §6). Every form the inference writes is a form an author may write, and the parser, the builder, `Prepare` and the executor accept and refuse the same text.
6. Every error names the author's repair (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §5). A refusal that records a mechanism's limitation is not an error about the query.
7. Cost is measured, never claimed (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §7), and an option that is off costs nothing.
8. The optimizer never changes results, and every test of this design runs under the optimizer-mode matrix of `RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §0.
9. The engine's contracts at the merge-base with `main`, `841caf8`, are the baseline. A change that drops a contract names the failure it removes. A mechanism of the merge-base's is not a contract: one that computed a form's interface from what it held (`NESTED_SCOPES_AS_QUERIES.md` §4), one that chose how a branch runs from the shape of its clauses, and one that bound into a branch what the form's header does not name (§4.2, §4.3).
10. A query is planned once per database per distinct prepared text and the symbols bound when the plan is made, whatever its inputs bind. The alternative is a plan made under a bound symbol kept out of the cache, so a query with a non-empty input is planned again on every execution.

## 2. The language

§2.1 to §2.5 of `NESTED_SCOPES_AS_QUERIES.md` stand. Two amendments state what the inference already writes.

### 2.1 A header of required variables alone

`(or-join [[?e ?f]] b1 b2)` and `(or-default-join [[?e ?f]] b1 b2)` are legal. The form keeps a tuple of the required run when a branch answers for it, and binds nothing. The `or-join` takes every branch's answer for every tuple. The `or-default-join` answers a tuple from the first branch with a result for it, and which branches are evaluated for a tuple is §4.2's. A `not-join` header is all required by definition.

The inference writes this header, by the rule of `NESTED_SCOPES_AS_QUERIES.md` §2.3, for a headerless form none of whose shared variables every branch binds: `[?e :a _] [?f :b _] (or-default [?e :x _] [?f :y _])` infers `(or-default-join [[?e ?f]] [?e :x _] [?f :y _])`, and an `or` of predicates over a variable a pattern binds, `[?e :n ?n] (or [(> ?n 3)] [(< ?n 2)])`, infers `(or-join [[?n]] [(> ?n 3)] [(< ?n 2)])`, the shape `TestOrJoinWithARequiredOnlyHeaderFiltersTheOuter` pins. A refusal of the header would reject a query the merge-base answered: the query `TestOrBranchExpressionIsOrderedAfterItsBinder` runs infers to `(or-default-join [[?a]] (and [(identity ?l) ?x] [?l :k :q]) (and [?m ?a _] [?x :q ?m]))`, the merge-base answered it with five tuples, and the test pins the five tuples on both planner paths. The alternative is the sentence of `docs/reference/OR_FALLBACK_SEMANTICS.md` that a per-group filter with no outputs is `or-join`'s job, which §10 replaces: the two forms keep the same tuples, and the fallback evaluates a later branch run per tuple only for the tuples the earlier branches left unanswered (§4.2). `Validate` refuses an empty header and a required run that overlaps the outputs, and nothing else about the header's shape.

### 2.2 A required variable the environment alone binds

A required variable that only a query input binds is legal for every form. The run carries the input's value in every tuple (`NESTED_SCOPES_AS_QUERIES.md` §5.4), and a header of such variables alone has the environment's one tuple as its run and the unit relation as its subject. For `or-join` and `or-default-join` the branches read it as they read any required variable. For `not-join`, and for the `not` that infers to it, the body runs over that one tuple and decides the whole scope: a body with a result empties every group, and a body with none leaves them, which is Datomic's `not-join` with its variables bound by `:in`. A header of such variables shares no data variable with the scope, and that is not a defect of the query. The inference writes this header for a headerless `not` reading only an input, `[?e :entity/kind "thing"] (not [?x :entity/flag ?flag])`, so a refusal of the header would refuse that `not` with a message about a form its author never wrote, against goal 6.

### 2.3 Refusals

§2.4 of `NESTED_SCOPES_AS_QUERIES.md` stands. Each refusal names the form, the branch by its position counted from one where a branch is at fault, the variable, and the repair. The header checks run at every boundary through one function, under the rule set at `Prepare` and with none at the text boundaries (§6).

The refusal of a variable a branch reads that neither the branch nor the header binds is one where a branch is at fault. It therefore names the branch by its position, and its repair, binding the variable in the branch or naming it in the header. The alternative, the form and the variable alone, leaves the author of a form with several branches to find the one at fault by reading each.

The refusal of a required run no order binds has two cases with two repairs. In the first, no input and no clause binds the variable, and the repair is binding it. In the second, some clause binds the variable and no order places that clause before the form, as when two forms each bind in one branch a variable nothing else binds, and the repair is the order. One computation tells the two apart on both planner paths: `query.NewNoOrderError` (`datalog/query/clause_ready.go`), which `orderClausesForCompile` (`datalog/algebra/compile_order.go`) and `createPhasesGreedy` (`datalog/planner/clause_phasing.go`) each return at their stall, names every clause left unplaced with the variables it waits on and appends "(no input or clause binds it)" to a variable with no input and no provider, and nothing to one with a provider; a clause waiting on no variable, which the planner's gates alone produce, is named as such. `Prepare` leaves this refusal to the planner (`NESTED_SCOPES_AS_QUERIES.md` §5.1), and goal 5 binds the two paths to one message for one text. Two alternatives are excluded. One message saying nothing binds the variable is false in the second case. A message per path, each stall rendering its own, refused one text with two messages and let the planner's say of a provided variable that nothing binds it.

A refusal the planner raises names the prepared form, the header the inference wrote included. A header's provenance is not a fact the engine holds (`NESTED_SCOPES_AS_QUERIES.md` §5.3), so the alternative, naming the written headerless form, has no input past `Prepare`. The header in the message is the inference's decision shown to the author, beside `Explain`, which plans the prepared query (`NESTED_SCOPES_AS_QUERIES.md` §5.1, pinned by `TestExplain_PlansThePreparedQuery`). The refusals `InferHeaders` itself raises name the written form, since they are raised on it.

## 3. The find boundary

One rule for both find kinds. A group the find does not read is an existence verdict: a group with no tuple empties the result, and a group with a tuple leaves the others as they are. The verdict is taken by one pull of the group's iterator, and an iterator filling a replay cache is read to its end before it is closed. With set semantics the projection of a product onto one factor's symbols is that factor when the other factor is non-empty and empty otherwise, so the verdict is the projection's own answer, and goal 3 of `NESTED_SCOPES_AS_QUERIES.md` ranks one rule for both find kinds over the merge-base's two.

The groups the find reads are returned as the group holding every find symbol, or the product of the groups that together hold them. Under aggregation, find symbols that span groups sharing no symbol are refused with the merge-base's message, the contract goal 9 keeps. The framed aggregating subquery of §4.4 never reaches that refusal: an inner query whose body reads no input is aggregated once and paired with every run tuple, so its find spans one group.

The merge-base's boundary, the baseline goal 9 names:

- A zero-symbol group and an all-environment group are absorbed, a non-empty one dropped and an empty one emptying the result.
- Every data group is kept.
- Under aggregation more than one group is refused, an unread data group included, empty or not.
- Under projection the one group holding every find symbol is returned and the rest are discarded, whether or not they hold a tuple.
- The product is taken when the find symbols span groups.

The rule above drops two of these: the aggregation refusal of an unread data group, and the projection discard. Goal 9 asks the failure each removal answers. Under the discard, a `:where` holding a pattern no tuple matches, sharing no symbol with the find, answers the other group's tuples, where a conjunction holding an empty relation is empty. Under the refusal, the same `:where` under an aggregate is refused as disjoint relations, whether or not the unread group holds a tuple. That refusal records a mechanism's limitation, which goal 6 says is not an error about the query.

## 4. The executor

### 4.1 One primitive

A scope is a header and a clause list. Each branch of an `or-join` or `or-default-join` is a scope under the form's header, a `not-join` body is a scope under its all-required header, and a subquery's inner query is a scope under its `:find` with its `:in` as the header's required run.

The primitive has two operations, the first the planner's and the second the executor's:

- `plan(scope)` is the planner's `PlanScope`: it frames the scope as the query `[:find <header> :in $ % :where (scope/required <required run>) <clauses>]` and plans it under the rule set. The scope is the planner's value, a header and a clause list, and the executor frames no query of its own. The text carries the binding and the scope is planned under no bound symbol, so the plan is cached under the text alone and made once per distinct scope text (`NESTED_SCOPES_AS_QUERIES.md` §5.2). The planner leads with `(scope/required …)`, and no rule set declares into `scope`. The readers of the `scope` kind are `RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §1.1's. A reader that wants a scope's clauses in the planner's order and runs nothing, the magic rewrite (`NESTED_SCOPES_AS_QUERIES.md` §5.5), reads the scope's plan as the planner made it, the phases' clauses in phase order less the `scope/required` invocation that opens them. Which passes a plan runs is the planner's decision. The alternative, the reader planning the scope under passes of its own choosing, puts that decision in the reader, which the sentence below excludes.
- `run(plan, run)` executes the plan with `run`, a relation carrying the required run's symbols by name, held under `scope/required` in a context that carries every relation the enclosing context holds, with `scope/required` rebound to this scope's run, and no environment. `(scope/required …)` binds each required symbol by finding it in the run's own symbols, never by its place in the run's layout, and a run lacking a required symbol is the query's error. It returns a relation of the header's symbols, by name. The alternative is the run read by position against the required list, which is correct only while one list builds both sides and is checked by nothing: a run laid out otherwise binds each value to the wrong variable and returns tuples, not an error.

The planner is the one orderer. No clause of a scope runs in written order, no loop beside the planner orders a branch's clauses, and no reader of a scope's order builds a planner of its own. The alternative is the merge-base's `executeInnerClauses`, which ran a branch's clauses in written order. There an expression written before its binder was skipped: `executeExpression` returns the groups unchanged when no group carries the expression's symbols. The branch of the query §2.1 quotes ran without its expression, and the merge-base answered the five tuples because that expression binds a local nothing reads. The failure the one orderer removes is at `5b152c9`, where the clause-based path panicked on that query when a tuple holding a nil value reached the fallback's tuple key.

### 4.2 The window

A branch's result for a subject tuple is a function of that tuple's projection onto the required run, by `NESTED_SCOPES_AS_QUERIES.md` §2.2, at every depth: a nested form reads its own header, a subquery its inputs, and a flat-header fallback inside a branch nothing of the branch. On the primitive that fact is an identity. For a run X over the required run, `run(plan, X)` is the projection onto the header of X joined with the branch's clauses, and join distributes over union, so `run(plan, X ∪ Y) = run(plan, X) ∪ run(plan, Y)`. Every clause the language admits inside a branch denotes a relation: a pattern, a predicate, an expression, a nested form over its header, a subquery framed as §4.4 frames it, and an invocation, whose rewrite seeded by X derives the selection of its predicate to X. The one shape that would break the identity, an aggregate over the run itself, has no spelling, since a branch's find is its header. So every partition of the distinct required run into batches answers the same tuples, provided the fallback decision reads a branch's result for the run tuple before the join on the carried outputs filters it (§4.3). A batch of one tuple is the merge-base's per-tuple evaluation, the whole run is its cached branch, and every batch size between them is as correct. A clause of a branch that binds a symbol the run binds unifies with it (`align.apply` in `datalog/executor/relation_ops.go`), so a result tuple carries its own run tuple on the required run, and the join on the header symbols both carry pairs it with that run tuple's subject tuples alone. What differs between batch sizes is cost and what is held. The plan's machinery, the hash join collapsing the held run with the pattern's result, the projection of the held run for `scope/required`, the materialized relations, the context derivation and the verdict, is paid once per batch. The matcher's work is paid per key either way at or below the boundary of §4.6. The subject tuples held are the batch's.

The executor runs every branch over a window of the subject. Every subject, whether or not it reports a size, is read into windows of one tuple, then two, doubling to the cap, each window holding its tuples and nothing of the subject beyond them, so the subject is read once and the first result follows one pull. The window's workspace grows with the window, by the same doubling and never past the cap, so a result abandoned after its first tuples, one the find boundary pulls once for its verdict (§3) or one read under a limit, has paid for the windows read and nothing more. The cap and the growth are options on `ExecutorOptions`, since a package-level setting is excluded by the janus `CLAUDE.md`, and the cap's default is the matcher's boundary of §4.6. Two alternatives are excluded. A workspace allocated at the subject's size when it reports one, the subject run as one window, reads every key of the subject before the first result, which an abandoned result pays for nothing. Growth without a cap holds about half the subject in its last window and allocates a larger workspace at every window; the cap bounds both.

Per window:

- The window's tuples are projected onto the required run, under the union with the carried outputs the subject carries (§4.4).
- The keys the kept index of §4.6 already answers are left out.
- Each branch's plan runs once over the keys that remain, through `run`.
- The results are indexed.
- Each window tuple probes the index, with the projection and the carried-output filters of §4.3 applying per tuple as they applied per subject tuple.
- Under the fallback a later branch runs over the keys the earlier branches left unanswered in the window, so no branch is evaluated for a key an earlier branch answered, and the hold before a window's first result is the window.

A branch reading nothing of what it is given, the required run under the fallback and the required run with the carried outputs under the union, where a branch reads a symbol when a clause consumes it that no clause of the branch provides or a data pattern mentions it, has the environment's tuple over the required symbols the environment alone binds as its run, the unit relation when there are none: one window with nothing of the subject in it, its result probed with no key. A lone ground is such a branch, and so is an uncorrelated subquery with no input, which is how the merge-base ran it. A form given nothing runs every branch once over the unit relation.

A branch holding an invocation runs over the window as any branch does, and its fixpoint is continued across windows. The sets of every stratum, the whole predicates' relations and the derived-tuple count are carried from window to window, a window's keys enter the seed predicate's stratum as a delta, and the strata re-run from the lowest one that changed. The result is one fixpoint over the whole run. The seed decides which keys the adorned predicates carry and never what a key carries, which is the magic-set correctness the rewrite rests on (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §1.3). Every read of an adorned predicate inside a body is at a key whose magic fact the same window derives from the body's own guard. An invocation under a non-monotone form is adorned only where its adorned predicate lies in a stratum below the rule's own, and is left unadorned otherwise (`NON_MONOTONE_FORMS_PROOF.md` T6), and a same-stratum invocation stands only where evaluation is monotone (`NESTED_SCOPES_AS_QUERIES.md` §2.5). So each window's closure from the carried sets is the least fixpoint above them, and by induction over the windows and the strata it is the fixpoint over the keys seen so far. Each derivation fires in exactly one window when the semi-naive delta copies cover every occurrence of a predicate that changed in the window, the lower strata included: a body with no same-stratum invocation gains a marked copy per lower-stratum occurrence and runs it over the lower strata's new tuples at the window's iteration zero, in place of the whole view, and in the first window those new tuples are the whole lower relations. One rewrite serves every window, since the rewrite is a function of the predicate and the adornment. The iteration bound is counted per window per stratum, the tuple bound over the carried count, the stratum's begin and complete events fire once per form execution, at the first window and the last, and every window reads the query's one snapshot. The alternative, a fixpoint per window seeded afresh, re-derives every tuple a later window's seed reaches, which is the fixpoint per subject tuple goal 2 excludes, at the window's grain. The zero-default count idiom with a rule inside its subquery, `(or-default [(q [:find (count ?r) :in $ % ?g :where (reaches ?g ?r)] $ % ?g) [?n ...]] [(ground 0) ?n])`, therefore costs one rewrite and one stratum evaluation whatever the subject's size.

The merge-base's gate returned at the first uncorrelated subquery without reading the clauses after it, so a branch whose later clause reads a required variable was framed over no required run and refused by the planner on both paths with that variable unbound, where the language answers it. Under the window a branch's run is read from every clause, as above. The merge-base's split, every `or-join` branch per tuple and a cacheable `or-default-join` branch over the whole outer, was one batch size per form chosen by the kind of the branch's clauses, the mechanism goal 9 names as no contract, and the window replaces both with one evaluation whose only parameter is the batch.

Nothing materializes the subject. A subject of several groups is joined into one by a fold of the hash join under the groups' common symbols. Each group after the first is the build side, held in the join index under its key, and the join so far is the probe side, streaming through it. So each group is opened once, the subject reports no size, and the subject itself is never held. Two groups sharing no symbol join under no key, every build tuple under one key and every probe tuple combined with each of them: their product. One group held per join is a bound, not a choice. A procedure emitting the product of two single-use relations, each read once, holds the whole of the one exhausted first, since the other's last tuple pairs with every tuple of it; with several groups it holds all but one. The build side is the group, never the join so far, so the fold holds the groups beyond the first and never their product. Three alternatives are excluded. Every group materialized, the merge-base's fold, holds every group and delays the subject's first tuple until every group is read. A product reopening its inner side per outer tuple opens a single-use group, a form's result among them, a second time. A lazy sequence over the inner side holds that group as cells, walks them once per outer tuple, and wraps a streaming relation alone, so a form's result as the inner side is reopened the same way.

### 4.3 `OrFallbackRelation`

`OrFallbackRelation`, the form's result (§4.8), and `OrFallbackIterator`, its iterator, are the executor's evaluation of the two branch forms over the window, kept from the merge-base and changed where it computed an interface or chose a strategy from the kind of a clause. Goal 9 keeps `OrFallbackRelation`: the merge-base's contracts are the baseline, and it carries them. The alternative is a new type carrying the same contracts, whose cost is retargeting every test §9's step 3 restores, since those tests pin the contracts by the names of its internals. `OrFallbackRelation`:

- iterates its subject lazily and reports no size
- runs each branch once per window through `run` and probes the window's index per subject tuple
- projects a branch tuple onto the subject's symbols and the header's outputs, filling the gaps from the subject tuple
- joins an output the subject carries by keeping only branch tuples that agree with the subject's value, never superseding it (`NESTED_SCOPES_AS_QUERIES.md` §2.3)
- joins an output the environment binds with the environment's tuple
- deduplicates its branches' answers under the union when the form has more than one branch, on the composite key the derived properties (§4.7) give, since two branches can answer one subject tuple and no property says otherwise, and under the fallback only when the subject carries no key, since one branch answers each subject tuple and a branch's answer is a set, which a set-preserving operator does not deduplicate again (the relational invariants of the janus `CLAUDE.md`)
- surfaces a subject scan failure and a branch failure when the result is driven, never as no match and never from the constructor
- copies a tuple at the boundary when its source reuses its workspace

`OrFallbackRelation` also gains:

- the branch cache, kept across windows, under either form (§4.6)
- the window of §4.2 in place of the merge-base's gate, which returned at the first uncorrelated subquery without reading the clauses after it, and in place of its two paths
- `run` in place of a loop over a branch's clauses in written order
- the fallback decision for a run tuple taken on the branch's result for that tuple, before any filter on the carried outputs. At the merge-base `nextShortCircuit` filtered a correlated branch's result against the outer tuple before deciding whether the branch answered. An output bound into a branch before a non-monotone decision changes the decision, the third example of `NESTED_SCOPES_AS_QUERIES.md` §2.3, so the decision reads the branch's result first and the join on the carried outputs follows.
- what a branch sees decided per branch:
  - Under the fallback a branch sees the required run alone, so an invocation in it is seeded by the header (§4.5), and its carried outputs the subject carries are joined with its result after the decision (§4.6).
  - Under the union a branch holding an invocation sees the required run alone, so the invocation is seeded by the header, and its carried outputs are joined with its result through the index's key.
  - Under the union a branch holding no invocation runs over the window's projection onto the required run and the carried outputs, its seek, after its plan over the required run alone is accepted (§4.4).
  - An output the environment alone binds is joined with the environment's tuple by the carried-output filter after the probe, under both forms.
  - One set of visible symbols for every branch of the form, the required run with every carried output, seeds an invocation inside a branch at a position the header does not name, which §4.5 excludes.

The evaluation is four modules every windowed form shares and a policy per form, the decomposition `OR_FALLBACK_RELATION_PROOF.md` derives. Each module is one lemma of that proof, reads nothing of the form, and is pinned by the lemma's tests:

- **The window reader** (the proof's L1) reads the subject's iterator into the windows of §4.2, yields each window with its ordinal, reports the subject's exhaustion, copies a tuple whose source reuses its workspace, and surfaces the subject's failure. It owns the subject-tuple, exhaustion and window events of §4.9.
- **The frames** (L2) are one frame per distinct required list among the branches' plans, each resolved against the subject's symbols and the environment's tuple. A frame's run over a window is the window's distinct keys less those an earlier window ran, and a frame of no subject symbol runs once over the environment's tuple or the unit relation.
- **The kept branch** (L3a, L3b) is the branch cache of §4.6 over a branch's result symbols, keyed on the header symbols the subject carries, built from a plan and a run through `run` and read whole, grown by every window's build and probed per window tuple. The EA arm of §4.6 is a second build under its own conditions. It owns the build event of §4.9.
- **The continuations** (L6) are the evaluations the branches' invocations continue across windows, owned by the outermost windowed form's iterator and shared by every form inside it.

A form composes them: a window is read, each frame's run is computed, each branch is built over its run, and each window tuple is answered by probing the built branches. The form's own policy has five parts:

- the framing of its branches (`planBranches` and `givenSymbols`): the union's seek and its plan over the required run alone, the fallback's required run alone, the `not-join`'s all-required header over one body, and the subquery's inputs with its find shape (§4.4);
- the emit rule: every branch's matches under the union, the first branch's under the fallback, the window tuple with no match under the `not-join`, and the one body's matches under the subquery, with the carried-output filter and the output projection shared by the three forms with outputs;
- the fallback's window step (§4.10), the prefetch of a window's entities above the threshold under the option, applied to the window as read, before any frame's run is computed;
- the fallback's narrowing of a branch's run to the keys the earlier branches left unanswered and its record of the keys a build answered (L3c), applied between the frame's run and the build;
- the deduplication rule of the bullet above and the properties of §4.7.

Two alternatives are excluded. One relation with a mode per form puts the subquery's framing seams and the fallback's answered keys inside the one loop, where a defect in the shared part reaches every form and a green test of one mode can mask another's, and reports a `not-join` or a subquery under the fallback's names. A relation per form each carrying the window writes the window reader, the frames, the kept index and the continuation ownership once per form. The proof's F1 names which lemmas read the form, and the split follows that line.

Where the merge-base's `OrFallbackRelation` computed an interface from what it held, the reader `NESTED_SCOPES_AS_QUERIES.md` §4 names as the defect, this design reads the header:

- The branch's visible symbols are the required run. Under the fallback form an output the subject carries is joined after the branch runs, never bound into it, since an output bound in before the decision changes the decision. Under the union a branch holding no invocation binds it as its seek and a branch holding one has it joined through the index's key, which §4.4 states.
- The relation's schema is the subject's symbols plus the header's outputs, and a local every branch binds is not in it.
- The symbols a branch's indexed result is joined with the subject on are the header symbols both carry: the required run, and under the union the carried outputs.
- The environment contributes a required symbol only when no group binds it.
- A required variable the environment alone binds narrows a branch's run as any required variable does.
- The projection's combination sites (`projectionPlan.project` and `agreeing` of `matchEmit`, the drain `emitCachedMatches` begins, and the EA-built branch) filter on the outputs the subject carries and let no branch value supersede one.
- A branch's run is the window of §4.2, never a size read from whether the form has join symbols.
- A branch cache keyed on every subject symbol a branch shares has no input: a form with an empty required run has the unit relation as its subject.
- A refusal of a required variable no group binds has no input: a required variable the environment binds is legal (§2.2).
- A nil-scope arm that unifies a headerless form on every shared free variable has no input under `Prepare`.

### 4.4 The handlers

- **`or-join`.**
  - The subject is the groups holding a header symbol, one group unmaterialized, several joined into one.
  - A branch holding no invocation is planned first over the required run alone, the language's scope, and that plan's refusal is the form's, naming the branch counted from one on both planner paths. The alternative is a plan with the carried outputs bound from the start, which runs a branch the language refuses: the cycle of two identities under a header that binds none of it.
  - Such a branch then runs over the window's projection onto the required run and the carried outputs, a seek that answers the same tuples for a monotone branch as binding the required run alone and joining the outputs after, since an output another clause binds is joined (`NESTED_SCOPES_AS_QUERIES.md` §2.3). The alternative is the run over the required run alone with the join after, which loses the seek on the subject's values that §7 pins for a flat `or-join`.
  - A branch holding an invocation runs over the window's projection onto the required run alone, and its result is joined with the window's tuples on the required run and the carried outputs through the index (§4.6).
  - With no group holding a header symbol the subject is the unit relation, each branch runs once over it, and the union joins at the collapse as a new group.
  - The result replaces the consumed groups (§4.8) and carries the subject's symbols and the outputs.
  - `OrClauseComplete`'s `semantics` is `"union"` when the subject is the unit relation and `"correlated-union"` otherwise, the fact the header decides, and the handler emits the or-clause events for every `or-join`, written or inferred (§4.9).
- **`or-default-join`.** The same `OrFallbackRelation` with short-circuit: per key of the window, the first branch with a result answers, and a later branch runs over the keys the earlier branches left unanswered (§4.2). The subject is the groups holding the required run, and the carried outputs are filtered after the decision, since an output bound into a branch before a non-monotone decision would change the decision.
- **`not-join`.**
  - The subject is the groups holding a header symbol.
  - The body is one branch under the all-required header, composed over the modules of §4.3: its frame's run per window is the window's distinct projection onto the header variables the subject carries, less the keys an earlier window ran; the body is built over that run; a window tuple whose probe returns nothing is yielded, and one whose probe returns a tuple is dropped.
  - The result is the subject's tuples with no match, in the subject's order, so it keeps the subject's keys and ordering, and it replaces the consumed groups (§4.8).
  - The subject is read once, and nothing of it is held beyond the window.
  - A header variable the environment alone binds is a constant on both sides and is no key.
  - A header the environment alone binds has the environment's one tuple as its run and the unit relation as its subject: the body is built once over that tuple, the unit relation's one tuple is dropped when the body has a result and kept when it has none, and the find boundary's verdict of §3 then empties the result or leaves it (§2.2).
  - An empty subject yields no window, builds nothing and yields nothing, which is the subject's own answer.
  - A failure of the body's scan is the form's error, surfacing when the result is driven.
  - The body is never run per combination: one run per window, the fixpoint of an invocation in the body continued across windows, is what keeps that invocation at one evaluation (goal 2).
- **Subquery.**
  - The inner query is one branch composed over the modules of §4.3, under §4.2's window over the relation of its argument combinations: the subject is the groups holding an input symbol, joined into one; the branch is framed over the data inputs as its required run with the binding symbols as its outputs; its frame's run per window is the window's distinct projection onto the inputs, less the keys an earlier window ran; the body is built over that run, and each window tuple's matches are yielded joined with the tuple. A repeated combination reads the kept branch and is not run again.
  - The call's substitution is the frame's own, read once from the text: each inner `:in` symbol stands for the argument at its place, and each inner `:find` element for the binding variable at its place, the unification `NESTED_SCOPES_AS_QUERIES.md` §5.5 states. The frame presents the run under the inner `:in` symbols, found in the subject by symbol. The scope is the inner query as written, its variables renamed apart from the enclosing scope's. The answer enters the kept branch under the enclosing names through `Relation`'s rename by symbol and, for an inner symbol written at an `:in` place and at a `:find` place, which two enclosing names stand for, the argument's and the binding's, a copy of its attribute under the binding's name through the identity expression, since a rename gives an attribute one name and the kept branch's key reads the argument's, so the probe, the carried-output filter and the emit, shared with the branch forms, read the enclosing names only, and the subquery's policy is its framing and nothing else of its own. The alternative is a rename inside the emit by position, against a find the frame composed, which holds only while the composed list and the answer's layout agree and is checked by nothing.
  - An aggregating inner query whose body reads an input is framed with its inputs as group keys.
  - One whose body reads no input is a pure aggregate: it is the frame of no subject symbol, built once at the first window and probed with no key, so it is aggregated once and paired with every run tuple, since adding group keys to a pure aggregate changes its kind (the janus `CLAUDE.md`, "Decorrelation Pure Aggregation Bug").
  - The binding names the inner query's outputs in the enclosing scope, and the result enters the scope as the relation over them, joined with the run. A binding asserts nothing about cardinality. The alternative is a one-tuple check under a tuple or scalar binding, a count over the result that the binding's spelling hides: an aggregate the inner `:find` does not show, non-monotone where the inner query reads the rule's own stratum, and taken only with the run grouped. A count is written in the inner `:find` as one.
  - A binding symbol the scope already binds is a carried output: the carried-output filter joins it with the result after the probe, and it is never bound into the inner query, whose inputs are its `:in` alone (`NESTED_SCOPES_AS_QUERIES.md` §2.5). Bound in before an aggregating inner query runs, it changes the aggregate.
  - A name written at two places of the binding unifies the two outputs it names (`NESTED_SCOPES_AS_QUERIES.md` §2.5): the presentation selects the tuples whose two outputs are equal and renames them to the one name, as the invocation's repeated argument selects on equality. The alternative is the later find element dropped at the presentation, which keeps a tuple whose outputs differ with one value lost.
  - A keyword that reaches an attribute position through an input is evaluated as data: the pattern seeks the attribute, and an entity that lacks it yields no datom, which a fallback form answers.
  - An entity carries any attribute, and the schema declares nothing about which attributes an entity may carry.
  - The refusal of an attribute the query names is an option decided at entry (`RULES_WITNESSES_AND_SPECULATIVE_VALUES.md` §4), never a rule of evaluation.
  - A scalar or tuple input is a position of the run.
  - A collection or relation input expands in the frame's key: one run tuple per member or per inner tuple beside the window tuple's values, so an invocation in the body is seeded once from every combination.
  - Inside a branch the combination relation is the branch's window (§4.2).
- **A data pattern over a streaming group.** The pattern is one body under the header of the variables it shares with the group, composed over the modules of §4.3 under the subquery's emit rule: the subject is the groups holding a shared variable, joined into one; the body is built once per window over the window's distinct keys less those an earlier window ran, each key sought by the matcher (§4.6); each window tuple is answered with its matches joined, the pattern's other variables as the outputs; the result stands in the consumed groups' place (§4.8), reports no size, and reads the subject once; and its keys survive when the pattern answers at most one tuple per subject tuple (§4.7). A group held in memory binds the pattern through the matcher, which reads it as bindings and joins the matches at the collapse, since nothing is copied to read it twice. The alternative is the matcher's bindings over a copy of the streaming group, joined back at the collapse, which §4.2 excludes: the copy is read once and discarded, and the collapse opens the consumed original a second time.
- **A bound invocation at the top level.** The invocation is one branch under the header of its bound variables as the required run and its free variables as the outputs, run as the union form (§4.3). The subject is the groups binding its arguments, joined into one. The branch runs over each window's projection onto the required run, its fixpoint seeded by the window's keys and continued across windows (§4.2, §4.5). Each window tuple is answered from the derived relation's index on the required run, and the result stands in the consumed groups' place (§4.8), reports no size, and reads the subject once. The window is for an invocation that derives its predicate at the clause (§4.5) over a group that reports no size, as for a data pattern. A group held in memory seeds the derivation through its projection onto the bound arguments and joins the result at the collapse, since nothing is copied to read it twice, and the run a frame holds per window is such a group, so the invocation a frame runs is seeded through the run and never windowed again. An invocation of a predicate the scope holds, a stratum's relation or its last delta under the fixpoint or the required run under `scope/required`, has no fixpoint to seed: it reads the held relation and joins it at the collapse, where the hash join holds the held relation and streams the group once, so it is never windowed whatever binds its arguments. An invocation binding nothing has the unit relation as its subject and runs once over it, the union joining at the collapse as a new group. Two alternatives are excluded. The seed read from a streaming group materialized and the collapse joining the group again holds the group whole and reads it twice. The window taken on the group alone, held predicates included, runs a framed plan per window of a body's pattern result for the join the collapse makes, at every iteration of every stratum.
- **Rule bodies.** `planBody` runs a body on the primitive as it does today.

### 4.5 Rules inside scopes

An invocation inside a scope evaluates at its clause, seeded from the scope's bindings at that clause, the required run and what the planned clauses before it provide, once per scope execution. The branch holding it runs over the window's projection onto the required run alone (§4.3), so the seed is the header's binding, one window's keys at a time, and the fixpoint is continued across windows (§4.2). Inside a rule body the scope's context carries the stratum's held relations, so a same-stratum invocation reads the delta and never derives at the clause. The magic rewrite reads the scope's planned clauses as `NESTED_SCOPES_AS_QUERIES.md` §5.5 states.

### 4.6 The branch cache, the seek and the EA arm

A branch's window result is indexed on the header symbols its result shares with the subject, the required run and under the union the carried outputs, in a `JoinIndex` the kept branch embeds (`cachedBranch`, `datalog/executor/kept_branch.go`), kept across windows and probed per subject tuple, the probe returning the key's group with no allocation; a branch sharing none has an empty key, and its probe returns the whole result. A key a later window carries again probes the index and is not evaluated again, which is the discipline the fixpoint's sets apply to a repeated seed. Under the fallback the index is on the required run alone, since the decision reads the branch's answer for the required key before the carried outputs are joined (§4.3). `JoinIndex`'s contracts, one group per distinct key in the order added, the key read at the probing relation's positions, every tuple one group under no key, two keys under one hash told apart, a key added again joining its group, an identity matched by value, a probe allocating nothing, and `KeysUnique` as the candidate-key proof, are pinned in `datalog/executor/join_index_test.go`. The index grows with the keys answered, a later window's tuples joining their keys' groups. The window's workspace is bounded by the cap, and the index is not.

The matcher's binding-driven scan narrows a scan to the bound value when the binding relation holds one distinct key, and for several keys leaves the bound at the pattern's constants and scans that extent once, probing each datom against the keys (`matchWithHashJoin` in `datalog/storage/hash_join_matcher.go`). For a key at the entity position with the attribute constant that extent is the attribute's. For a key at the attribute position with the other positions variable it is the whole index. So a window of several keys on a large attribute reads the attribute, where the per-tuple path read one narrowed scan per tuple. The matcher therefore gains a per-key seek strategy beside the hash-join scan and the merge join: one narrowed scan per distinct key, the bound the one-key narrowing produces, yielded as one datom stream that the hash-join iterator consumes as it consumes the wide scan, so the join, the constraints, the CRDT resolution and the tuple building are unchanged. It is chosen where the one-key narrowing is decided, after `buildHashSet` has counted the binding's distinct keys: at or below the boundary `chooseJoinStrategy` carries between a small binding set and a large one, the keys are sought one by one; above it the hash-join scan and the merge join stand as they are, and `chooseJoinStrategy` keeps reading the binding's `Size()` for the choice between them. A key at the attribute position is sought per key at any count, since the attribute is the prefix of its own index. A key the index cannot bind, a value that is not a reference at the value position, whose one-key bound is the pattern's own, is probed against the one scan of the extent at any count, since a seek per such key would read the extent once per key where one scan of it serves every key. The engine carries no statistic of an attribute's extent and estimates none. The keys in hand are the visible selectivity the planner's greedy ordering rests on (`docs/papers/STATISTICS_UNNECESSARY_PAPER_OUTLINE.md`): the seeks' cost is bounded by their count, and the extent's cost is a number the engine cannot see. The strategy reports one scan-funnel completion event of its own, named in `datalog/annotations/types.go` beside the hash-join and merge-join events, carrying the same funnel and the key count. The window's cap defaults to the same boundary, so a full window is sought per key.

A branch of one data pattern on the default source, whose entity position is a required variable the subject carries, with the attribute declared cardinality one and the matcher non-temporal, the conditions the matcher's `CanFuseAttributeFetch` states for substituting a lookup for a scan, asked for the pattern's source (§4.7), is built from the EA cache through `buildBranchFromEACache` under `EnableEntityPrefetch` (§4.10): one `LookupAttribute` per distinct entity of the window, the environment-bound value narrowing the result when that value is in the required run. The source condition holds because an entity lookup is the default source's answer, which the executor's attribute-fetch fusion already requires of the pattern it fuses. The built tuples are kept under the key of every run symbol the subject carries, so a required value the subject carries is compared at the probe, as the scan path compares it through the run. No warmth is read, and §7 pins that the arm answers as the scan path does whatever the cache holds, with the value symbol required as with it free. The arm runs under the option that runs the prefetch, whose warm cache is the arm's benefit, so a query with the option off pays nothing for it (goal 7), and §8 measures the arm with the option on and off. A branch that fails a condition takes the matcher's path above.

### 4.7 Properties

The `OrFallbackRelation` derives the result's properties through `orProperties` from the subject's properties and the header:

- The outputs are what the branches produce, and nothing is overwritten, since an output the subject carries is joined and never superseded (§4.3), so no subject symbol drops its key or ordering on the branches' account.
- Whether every branch answers at most one tuple per subject tuple is judged against the header symbols the subject carries, the grain the result is produced at.
- That judgment reads properties: an expression binding one value, a subquery whose find is aggregates and variables the subject carries, whatever its binding's spelling (§4.4), and a data pattern whose entity position is a required symbol the subject carries, whose attribute is a constant, and whose attribute resolves to one value per entity under the handle, which the matcher states through `CanFuseAttributeFetch`, cardinality one and no `History`, the two facts §4.6 names, so the executor reconstructs neither; the capability takes the pattern's source, as `AttributeVocabulary` does, so a router answers from the source named. The alternative is a judgment by the kind of a clause alone, under which a data pattern never answers at most one, so the subject's key is dropped through every pattern branch and the union deduplicates on a composite key the properties do not require; and the cardinality read from the schema in the executor, which omits the mode, under which a pattern under `History` answers every version and the key the result claims is false.
- A subject's ordering survives both forms. Its key survives under the fallback when every branch answers at most one tuple; otherwise the result's key is the composite of the subject's key and the produced outputs, under the union always, since two branches can answer one subject tuple.
- The derivation emits `OrPropertiesDerived`.
- Every reader of the properties, the projection's dedup elision, the join's strategy and build side, and the scan-boundary restoration, takes the decision it takes on the merge-base for a result the `OrFallbackRelation` produces.
- A union over the unit relation (§4.4) is a new group with the full-header key and no ordering, and no subject property reaches it.
- The `not-join` keeps its subject's properties, since it yields a subset of the subject's tuples in the subject's order (§4.4).

### 4.8 Group replacement and read-once

The form's result replaces the consumed groups through `replaceConsumedOrGroups`, with no join at the collapse, and emits `OrOuterReplaced`. A streaming subject is read once: the result stands in the subject's place, and a reader that needs the result twice materializes the result, never the subject.

### 4.9 The events

Every name in `datalog/annotations/types.go` whose fact this mechanism produces emits with `main`'s payload: `OrClauseBegin` and `OrClauseComplete` from the or-join handler, `OrClauseUnion` and `OrClauseBranchComplete` from the unit-run route, `OrPropertiesDerived` from the derivation, `OrOuterReplaced` from the replacement, and `OrFallbackIteratorCreated`, `OrFallbackBranchNarrowed` and `OrFallbackBranchSuccess` from the `OrFallbackRelation`. `OrFallbackOuterMaterialized` has no fact to report, since nothing materializes the subject (§4.2). The modules of §4.3 report their own facts under every form: the window reader reports each subject tuple read, the subject's exhaustion, and each window with its ordinal, its tuple count and its distinct key count over the required run's symbols the subject carries, and the kept branch reports each window's build with the branch, its symbols and the tuples built. Those four events are named in `datalog/annotations/types.go` for the module under the `scope` family, each carrying the form it fired under. The alternative, the `or-fallback` names for them, records a fallback under a `not-join` or a subquery that ran none, and a reader of `Analyze` cannot tell the form from the name. The handlers' own contract:

- The fallback handler emits its `OrFallbackRelation`'s events and no or-clause event.
- The completion event of a streaming form fires at construction with size -1, and a branch failure surfaces when the result is driven.
- A scope's run emits no `PhaseBegin` and no `PhaseComplete`: the form's own events report a branch's execution, and a phase event per window would be a handler call per window beside the window's own event.
- A stratum continued across windows emits `RulesStratumBegin` at the first window and `RulesStratumComplete` at the last, and its `RulesIteration` events number each window's iterations from zero (§4.2).
- §7's counts of branch executions read the kept branch's build events.

Preparation is a fact of its own. The executor's entry emits `QueryInvoked` with the query as received and `QueryPlanCreated` with the plan (`ExecuteWithRelations`, `datalog/executor/executor.go`), and `Prepare` runs between them with no event, so a handler sees what the inference wrote only by comparing those two renderings, neither of which is the prepared query, and `Analyze`, which sums latency per event name, attributes preparation's time to no event. One event, named in `datalog/annotations/types.go` beside `QueryInvoked`, is emitted after `Prepare` under the same call-site guard, carrying the prepared query's rendering, whether the inference rewrote a form, which `InferHeaders` computes when it returns the query it was given, and preparation's time. A query with no handler pays nothing for it, as for `QueryInvoked` (goal 7). The alternative, the prepared text as a payload of `QueryPlanCreated`, puts two facts under one name where `Analyze` reads one fact per name, and reports nothing when planning refuses the prepared query, since that event fires after planning.

### 4.10 Prefetch

One option, `EnableEntityPrefetch`, governs every prefetch trigger, so a query with the option off pays nothing (goal 7). The executor's trigger after the first data pattern stands as on `main`. The fallback's trigger, Rule 6's first trigger point in `docs/ALGEBRA.md`, is the policy's window step of §4.3 (`prefetchWindow`). It runs under the same option. It reads the window's distinct entities at the subject's positions of the entity symbols the branches of the EA arm's shape read.
