23. **`Size()` semantics and sizing economics** — RULED AND DOCUMENTED (2026-07-21). CORE_MODEL Pillar 3's "Size() peek-and-consume" claim did not describe the implementations: no `Relation.Size()` consumes the caller's tuples — each answers free, answers -1, or self-realizes into the pass-through materialized form (spending only an owned upstream source). The economics ruled: stream consumption is the default optimum; realizing for a size pays only when incremental processing is expensive or the realized relation is itself passed through directly afterward; a capacity hint must never be the call that forces work. Call-site behavior left as-was by explicit ruling (the materialized-only pre-allocation guards in `relation_ops.go` stand); any change is a separate discussion. The peek hazard re-aimed at uncaptured iteration. Follow-on ruled and executed (2026-07-21): **`Relation.IsEmpty()` deleted** — bool cannot decline the way `Size()`'s -1 does, so streaming implementations either lied (`StreamingRelation` returned hardcoded `false` in the default mode) or consumed (`OrFallbackRelation` stepped an iterator); the engine carried four "don't call IsEmpty" warnings around it. All seven implementations removed; the three production callers converted — `Size() == 0` at both matcher empty-binding sites (subsuming their `*StreamingRelation` type-guards; the -1 decline is the guard) and consume-then-decide in the table formatter; test assertions converted to exact Size/iteration forms, none weakened. Extended by owner ruling same day ("the entire concept is a virus"): every remaining `IsEmpty` eradicated — `BufferedIterator.IsEmpty()` (zero production callers), `query.Relation.IsEmpty()` (zero callers), `OrderedSet.IsEmpty()` (tests converted to `Len()`), the last stale don't-call comments, and the live interface listings in ARCHITECTURE.md / RELATIONAL_ALGEBRA_OVERVIEW.md / ARCHITECTURAL_PHILOSOPHY.md (whose mistake table also carried the false "Size() forces materialization, may lose data" row — corrected).
