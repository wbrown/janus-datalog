## The finding (from the owner's review of the pushed rework, at `fe76a42`)

`[:find ?e :in $ ?flag :where [?e :entity/kind "thing"] (not-join [?e ?flag] [?e :entity/flag ?flag])]` diverges between planner modes: the algebra (default) mode hard-errors `not-join header symbol ?flag is not bound by the outer relation` (algebra/compile.go:346), while `-optimize=false` returns the correct 2 rows (the reviewer verified: `executeNotJoinClause` bridges the `:in` scalar into the subject via `findOuterRelation`, query_executor.go:2005). The well-formed sibling (param consumed by the body, not declared in the header) agrees on both modes today.

## The ruling: ACCEPT is canonical — the algebra header validation is the stale side

Four grounds, strongest first:

1. **Datomic compatibility.** Datomic has no environment/data distinction — `:in`-bound variables are ordinary bound variables, and `(not-join [?e ?flag] ...)` with `?flag` from `:in` is plainly valid Datomic. Rejecting it is a janus-specific incompatibility manufactured by an internal implementation distinction the language deliberately does not expose.
2. **Inference-form coherence.** The bare `not` with an `:in`-bound correlate is pinned correct on both modes (`TestNotBodyConsumesInBoundParameter`, mode-matrixed, from the anti-join bridging arc). `not-join` differs from `not` only in declaring explicitly what the bare form infers; a language where naming the inferred interface is an error has a corner that exists for no semantic reason.
3. **Or-join symmetry.** The item-24 ruling settled this for the other explicit-header family: environment symbols join into branch evaluation regardless of the header, the wide-header `:in`-bound or-join shape is pinned must-keep-working, and the correlated compile route "preserves the declared header verbatim" (compile.go:401-409). `not-join` rejecting what `or-join` accepts splits the explicit-header forms.
4. **The declaration is vacuous truth, not error.** The anti-join key component for an environment symbol matches trivially against the environment's single row — exactly like declaring any join variable that happens to be single-valued, which is invalid nowhere else in the language. The executor's bridging path already implements precisely this semantics, verified 2 rows by the owner's review.

The environment ruling (ledger item 24) makes the domain precise: Available = outer data ∪ environment in every clause scope. The compile check judges boundness against outer data alone — the pre-ruling world. Same class as the narrow-header lowering bug the bridging arc fixed: a boundary that forgot the environment.

## The class fix — four homes (resolved 2026-07-22 by reading `Analyze` and probing all shapes)

The first proposal ("fix compile.go:345") was a one-arm patch; the completion pass widened it to three arms; reading `Analyze` widened it again. The binding-domain error lives in **four** homes:

**Home 1 — `compileNotJoin` (algebra/compile.go:330-387)**: three arms judge "bound by the outer relation" against `current.Symbols()` alone, and none consults the `inputs map[query.Symbol]bool` already in the function's signature (only the inner-compile seeding at line 335 uses it):

1. **Lines 344-347** — header symbols vs `current.Symbols()`: the check the reviewer hit. Fires first, so it also masks arm 2 for declared-header shapes.
2. **Lines 349-361** — `right.Required` (from `Analyze(inner)`) vs `current.Symbols()` (line 353's "body requires unbound outer symbol") and vs the header (line 356's "header must declare outer requirement").
3. **Lines 363-375** — declared symbols neither in `inner.Symbols()` nor in `right.Required` error as "neither produced nor consumed"; survivors become the `AntiJoin`'s `Required`.

Fix: the function's binding domain becomes `current.Symbols() ∪ inputs` everywhere it judges boundness.

**Home 2 — `compileNot` (algebra/compile.go:272-327)**: line 296-297 rejects body free requirements not in `current.Symbols()` ("NOT body requires unbound outer symbol") — the same pre-environment boundary. A bare `not` whose body consumes the `:in` parameter only via a predicate dies here on the algebra path while the baseline executes it correctly (`notBodyBinding`, verified 98087 on the real module). Same domain fix; env symbols then flow into `joinSyms`/`required` exactly as WHERE-bound predicate-only correlates do.

**Home 3 — `analyzeAntiJoin` (algebra/analysis.go:344-395)**: resolves the READ-BEFORE-EDIT unknown. `Analyze` has **no inputs parameter at all** — `Required` is pure bottom-up free-variable propagation, so the green omitted-header shape was explanation (a): the body pattern *provides* the symbol, keeping it out of `Required`. But `analyzeAntiJoin` independently enforces the pre-environment world twice: every `data.Required` symbol must be **produced by the left child** (lines 356-357) and every `JoinSymbols` entry must be **produced by the left child** (lines 366-368). `Analyze(root)` runs over the full tree in `RefreshSchemas` (analysis.go:157) and at the top of the join-project pass (rewrite_project.go:13), so fixing homes 1-2 alone just moves the error. Fix: a symbol not produced by the left child becomes a **free requirement of the AntiJoin node** instead of a validation error — exactly how `analyzeSelect`/`analyzeMap` already treat unproduced `Required` (propagate upward, lines 260-264/304-308), and the escape hatch already exists (`antiJoinFreeRequirements`, line 393). `Analyze` cannot and need not distinguish env from typo: typos still die at compile time in homes 1-2, whose domain is `current ∪ inputs`; `Analyze`'s job is schema and freeness, and freeness propagates to the root, where free requirements are precisely the query's environment demands (already the model for `:in` params consumed by top-level Select predicates).

**Home 4 — executor `filterWithNotJoinClause` (query_executor.go:2159+)**: lines 2174-2178 validate every header var against the **subject data relation's** symbol set — *before* `notBodyBinding` joins the environment into the body's binding domain at line 2182. A declared env symbol the body consumes only via a predicate dies here on the **baseline** path too ("not-join variable ?name is not bound in the subject relation" — probed on the real module, both empty and data-present). Fix: the header validation domain becomes subject ∪ environment, and the join-key machinery splits accordingly — `getUniqueCombinations(input, clause.JoinVars)` (line 2188) and `keyIndices` (line 2129) must source env-bound header vars from the environment's single row and data-bound vars from the input relation. (Pattern-provided declared shapes never reach this error because the body produces the symbol; the bridging arc's `findOuterRelation` path handles those, verified 98087.)
